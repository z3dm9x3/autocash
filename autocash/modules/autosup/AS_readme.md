# AS — Autosup

Модуль узнаёт ID игрока (MelID) в личных сообщениях. Работает в фоне, только с личными сообщениями, по протоколам Role Manager.
Решения: `docs/decisions.md`, D-AS-1…D-AS-4.
Autosup — модуль общения с игроком. Тикеты ведёт отдельный модуль Ticket System (`ticket_system/TS_readme.md`,
D-TS-1…D-TS-3): Autosup передаёт ему каждое личное сообщение игрока и пишет в `logs` его результаты.

## Что делает

| Событие | Действие Autosup |
|---|---|
| `contact.first` — человек написал впервые | ждать 60 секунд с первого сообщения: ID за это время (и в первом сообщении) — взять и закрепить без вопроса; нет ID — отправить «Здравствуйте!\nПришлите ваш ID» и ждать дальше |
| `contact.second` — человека нет в базе, но переписка была | искать ID в истории диалога: найден один — взять его; не найден — как при первом контакте (60 секунд, затем вопрос), диалог помечен `second` |
| сообщение пользователя, пока Autosup ждёт ID | первое сообщение с ID: записать игрока и закрепить сообщение. Сообщения без ID ожидание не прерывают |

Когда ID получен:
1. RM: игрок (`rm_players`), его MelID (`rm_player_mel`), ссылка `rm_users.player_id`.
2. ID без пробелов — закрепляется сообщение пользователя.
3. ID с пробелами (`123 456 789`) — Autosup отправляет его без пробелов (`123456789`) и закрепляет своё сообщение.

Если MelID уже записан за другим игроком, пользователь присоединяется к этому игроку: один человек, несколько аккаунтов. Если у пользователя уже есть свой, другой игрок, склейки нет — сообщение уходит в `logs`.

Ожидание ID заканчивается через 7 дней (`expired`).

## Команды

| Команда | Где | Что делает |
|---|---|---|
| `/as on` | группа с ролью tech | включить Autosup |
| `/as off` | группа с ролью tech | выключить: ничего не пишет и не начинает ожиданий |
| `/as` или `/as ?` | группа с ролью tech | состояние: включён ли, сколько ждут ID, сколько получено |

Права — Admin и Dev. В другом чате — ответ «работает только в группе с ролью tech». Без прав — в чате ничего, отказ в `logs`. Включение и выключение пишется в `logs`. Состояние хранится в `as_settings` и переживает рестарт.

## Распознавание ID (`AS_ids.py`)

Правила выведены из 1 211 реальных ответов на «пришлите ID» и 6 410 реальных MelID (Cash Monitor Dev, 2026-11-18):

- ID — **8–12 цифр** после удаления пробелов: `1234567890`, `123 456 789`, `1 234 567 890`. Суммы не длиннее 6–7 цифр (максимальный депозит — 500 005).
- **Не ID:**
  - телефон: `+7…`; 11 цифр с 7 или 8; 10 цифр с 9 — у настоящих 10-значных MelID первая цифра 1;
  - число, приклеенное к буквам (имена файлов чеков);
  - число после «Заявка #», «EPOS ID»;
  - число рядом с «руб», «₽», «тыс», «сумма», «реквизиты», «карта».
- Префиксы `ID`, `Id`, `I'd`, `айди`, `ид` и подпись «Номер аккаунта» допускаются.
- Несколько разных ID в одном сообщении: берётся подписанный; если подписанного нет — ничего не угадываем.
- Нули подряд разрешены: у 30 настоящих MelID есть «000».

## Обратная связь (AGENTS.md, правило 9)

Пользователю Autosup пишет только это:
- просьбу прислать ID;
- нормализованный ID, если пользователь написал его с пробелами;
- закрепление сообщения с ID.

Всё — через Outbox (`send`, `pin`), привязано к аккаунту диалога. Создание игрока пишется в журнал монитора.

В `logs` Autosup пишет:
- совпадение MelID с другим игроком;
- тип каждого тикета TS, по одной записи на тикет (протоколы `ticket.d|ww|q`, D-TS-3):
  `TS: тикет #123 — D · игрок 123456789 (@ник, MelID …) · аккаунт … · триггер: «пополнил»`.
  Эти записи не зависят от `/as on|off`: переключатель касается только сообщений игроку.

## Передача в Ticket System

Каждое новое личное сообщение игрока (не персонала: casher, support, manager, admin, dev) Autosup передаёт в TS
(`TS_api.receive`) вместе с `media_type` из `messages`. Если `modules.ticket_system` нет в конфиге, ничего не
передаётся.

## Конфигурация (`modules.autosup.config`)

| Ключ | По умолчанию |
|---|---|
| `ask_text` | `Здравствуйте!\nПришлите ваш ID` |
| `grace_s` | 60 — сколько ждать ID без вопроса после первого сообщения |
| `wait_days` | 7 |
| `history_messages` | 500 — глубина поиска во втором контакте |
| `history_days` | 180 |
| `ticket_log_text` | `TS: тикет #{id} — {ticket} · игрок {player} · аккаунт {account} · триггер: {trigger}` |

История читается через лимитер аккаунта с фоновым приоритетом. Это чтение, лимит отправок на него не действует.

## Таблица `as_dialogs` (`AS_migrations/001_as_dialogs.sql`)

`tg_id`, `account_id`, `contact` (first/second), `state` (grace / awaiting_id / done / expired), `contact_at` (первое сообщение), `ask_at` (конец 60 секунд), `asked_at`, `expires_at`, `mel_id`, `found_in` (reply/history), `msg_id`, `player_id`.

`as_settings` — переключатель `/as on|off` (`AS_migrations/002_as_grace_switch.sql`).

## Зависимости (явные)

- **Role Manager:** протоколы `contact.first` / `contact.second`; `RM_store.link_player`; таблицы `rm_players`, `rm_player_mel`, `rm_users.player_id`, `rm_users.username`; `SERVICE_USERS`.
- **Ticket System:** `TS_api.receive`, протоколы `ticket.d` / `ticket.ww` / `ticket.q`.
- **Ядро:**
  - Outbox — `services.outbox`, действия `send` / `pin`;
  - `services.read_dialog`;
  - `Module.private_dialogs` и `Module.protocols`.
