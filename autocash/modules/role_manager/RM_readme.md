# RM — Role Manager

Первый модуль Autocash. Ведёт пользователей, группы, роли и права в PostgreSQL.
По роли группы ядро решает, читать ли её; по роли пользователя — какие команды ему доступны.
Решения: `docs/decisions.md`, D-RM-2…D-RM-9 (D-RM-1 заменено D-RM-7).

## Команды

| Команда | Что делает |
|---|---|
| `/urole <TGID> <роль>` | роль пользователя (пользователь должен быть в `rm_users`) |
| `/urole <TGID>` | показать роль пользователя |
| `/grole <ID группы> <роль>` | роль группы |
| `/grole <ID группы>` | показать роль группы |
| `/grole <ID группы> -<роль>` | снять роль: группа получает `other` |
| `/rm set <ID> <роль>` | то же, что `/urole` или `/grole`: по роли понятно, пользователь это или группа |
| `/rm ?` | в группе: роль этой группы |

- Роль пишется любым регистром: `Admin` = `admin`.
- Нет совпадения (пользователя нет в базе, группа неизвестна, роли нет) — команда отвечает автору, что не так, и ничего не меняет.
- Команды принимаются и в группах, которые не читаются (`other`): сохраняется только сообщение с командой (D-RM-4).

### ID группы

Принимаются все четыре формы: `3845234572634`, `1003845234572634`, `-3845234572634`, `-1003845234572634`.
Записывается без минуса и без «100» супергрупп: `3845234572634` (D-RM-3).
Группа ищется среди групп, где состоят аккаунты пула, групп с ролью и источников конфигурации.

## Роли

| Пользователи | Группы | Политика группы |
|---|---|---|
| Guest — по умолчанию | Other — по умолчанию | `presence`: известна, не читается, реакций нет |
| Player | Tech | `full`: читается и обрабатывается |
| Casher | Dop | `full` |
| Support | WW | `full` |
| Manager | | |
| Admin | | |
| Dev | | |

## Права

- Права есть только у пользователей, роль группы на них не влияет.
- **Admin** — все команды: строка `admin → *` в `rm_permissions`.
- **Dev** — все команды всегда. Это правило кода, а не строка таблицы: Dev нельзя случайно лишить доступа.
- Остальные роли пока без команд. Право добавляется строкой `rm_permissions (role, command)`.

## Обратная связь (AGENTS.md, правило 9)

| Случай | Кому | Что |
|---|---|---|
| команда выполнена или отклонена по сути | автору, в чат команды | результат или причина |
| роль изменена | группе `logs` | кто, было → стало, автор |
| роль изменена | пользователю или группе, чья роль изменилась | **ничего** |
| нет прав | в чат | **ничего** |
| нет прав | группе `logs` и журналу монитора | «Отказ в правах: пользователь, роль, команда, чат» — в `logs` не чаще раза на пользователя в 10 минут, со счётчиком попыток |
| чужая команда (`/start` и т. п.) | — | никакой реакции |

Ответ автору приходит в тот чат, где дана команда. Чтобы участники группы его не видели, давайте команды из лички с аккаунтом пула или из служебной группы.

## Таблицы (`RM_migrations/001_rm_directory.sql`)

| Таблица | Поля |
|---|---|
| `rm_roles` | `code`, `scope` (user/group), `title`, `policy` (только группы), `sort` |
| `rm_users` | `user_id`, `tg_id` (уникальный), `username`, `role`, `source` (dm, import:cmd, cli, seed, manual), `had_dm`, `contact_protocol` (first/second), `contact_at`, `created_at`, `updated_at`, `updated_by` |
| `rm_groups` | `group_id`, `group_tg_id` (без минуса, уникальный), `title`, `role`, `casher_id` (позже), `updated_by` |
| `rm_permissions` | `role`, `command` (`*` — все) |
| `rm_history` | `at`, `author`, `entity` (user/group), `tg_id`, `before`, `after` |

Роль проверяется по области: пользователю нельзя выдать роль группы и наоборот (составной внешний ключ).

## Когда PostgreSQL недоступен

Ядро держит роли в памяти (`Directory`) и в файле `directory.json` рядом с буфером SQLite. При запуске оно сначала читает файл, затем RM загружает таблицы. Шлюз (какие группы читать) и права работают и без PostgreSQL. Изменить роль без PostgreSQL нельзя.

## Протоколы первого и второго контакта (D-RM-11, D-RM-12)

Срабатывают на личное сообщение человека любому аккаунту пула, если его TGID нет в `rm_users`:

| TGID в `rm_users` | Переписка с аккаунтами раньше была | Что происходит |
|---|---|---|
| есть | — | ничего |
| нет | нет | `contact.first` |
| нет | была | `contact.second` |

- «Была ли переписка» — сначала по нашей базе, затем один `getHistory` через лимитер; если Telegram не ответил — считаем «была».
- RM первым записывает пользователя (guest, `source=dm`) в той же транзакции, что и запуск протокола (`protocol_runs`), поэтому протокол срабатывает один раз на человека.
- Другие модули участвуют, объявив `protocols = ["contact.first", ...]` и `on_protocol(...)`. Сейчас таких модулей нет: запуски фиксируются и закрываются.
- Пользователю RM ничего не пишет. Импорт протоколы не запускает.

## Начальное заполнение и импорт (`RM_cli.py`)

Раздел `users` из конфигурации убран (D-RM-10): единственный источник — PostgreSQL.

    python -m autocash.modules.role_manager.RM_cli --env-file <pg.env> user <TGID> dev
    python -m autocash.modules.role_manager.RM_cli --env-file <pg.env> import-cmd --source-ini <settings.ini Cash Monitor Dev> [--roles-csv <файл>] [--dry-run]

`import-cmd` читает базу Cash Monitor Dev только на чтение, пишет пачками, Telegram не трогает (D-RM-13).
Роли ADMIN/CASHER оттуда не переносятся — список уходит в CSV для ручного разбора.

## Зависимости от ядра (явные)

- `autocash/core/directory.py` — `Directory`: роли в памяти и снимок.
- `autocash/core/commands/rights.py` — `can_run`, `deny`.
- `autocash/core/config/loader.py` — `bare_group_id`, `Runtime.source`: роль группы из `Directory` важнее ролей из `sources`.
- `autocash/core/gateway/gateway.py` — приём команд из групп, которые не читаются (`commands_any_chat`).
- `autocash/modules/api.py` — `Module.start`, `Module.commands_any_chat`, `Module.private_dialogs`, `Module.protocols`, `Services.dialog_history`.
- `autocash/core/protocols.py` и таблица `protocol_runs` (миграция ядра 010) — протоколы.
- `autocash/core/queue/manager.py` — доставка всех личных сообщений модулям с `private_dialogs`.
