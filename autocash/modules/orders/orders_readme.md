# orders — заявки на депозит и вывод

Модуль хранит депозиты и выводы касс. Пока он заполняется из архива Cash Monitor Dev (PostgreSQL :5433) и отвечает на команды персонала `/dev`. Решения: `docs/decisions.md`, D-ORDERS-1…D-ORDERS-7, D-OBX-8. Форматы карточек: `knowledge/deposits.md`, `knowledge/withdrawals.md`.

## Что хранится

| Таблица | Что |
|---|---|
| `orders_deposits` | депозит по `Deposit ID`: TGID, MelID, тип пользователя, запрошенная сумма (`amount`), сумма чека или зачисления (`receipt_amount`), метод без лимитов, касса и история касс (`chats`), статус, инициатор и причина отмены, время создания, чека, финала |
| `orders_deposit_messages` | каждая карточка депозита: `request` (заявка), `receipt` (`[ДЕПОЗИТ]` с чеком), `cancel` (отдельное «❌ Заявка #N отменена»), `accepted` (Top Pay «✅ Депозит принят #N»); поля разбора в `fields` |
| `orders_withdrawals` | вывод — одна карточка `[ВЫВОД]`: TGID, MelID, платформа, код, сумма, метод, реквизиты, банк, итог проверки кода (`success`, `fail` с текстом и кодом, `bare_ok`/`bare_fail`, `none`) |
| `orders_history` | состояние чтения архива: до какого `raw_messages.id` прочитано, пауза, конец первого прохода, последняя ошибка |
| `orders_history_chats` | группы, где бот платформы публиковал карточки (группы касс), с названием из архива |
| `orders_history_senders` | кто писал в какой группе архива: люди в группах касс — персонал |

Номера, реквизиты и коды хранятся как есть (AGENTS.md, инвариант 8).

### Статус депозита

Статус вычисляется из всех карточек заявки, поэтому порядок их прихода не важен (`orders_deposit_recompute`):

| Статус | Когда |
|---|---|
| `success` | `[ДЕПОЗИТ]` с «✅ Успех» / «✅ Подтверждено», или Top Pay «✅ Депозит принят» |
| `rejected` | в `[ДЕПОЗИТ]` дописана отмена (кассир отклонил чек), или голый `❌` в конце карточки чека |
| `cancelled` | заявка отменена: в карточку дописано «❌ Заявка #N отменена» или пришло отдельным сообщением |
| `receipt` | чек есть, итога нет |
| `open` | только заявка |

Перенаправленная заявка (та же `Deposit ID` в другой кассе) — одна строка, кассы по порядку в `chats`.

## Разбор — в PostgreSQL

`orders_parse(text, media)` (SQL, регулярные выражения) превращает текст карточки в вид и поля или возвращает `NULL`. `orders_apply` записывает карточку. Более старая версия текста никогда не заменяет новую: сравниваются `edit_date` и дата сообщения. Тот же разбор возьмёт живой приём, когда Autocash заменит монитор. LLM не используется.

## Чтение истории Cash Monitor Dev

Всё происходит внутри PostgreSQL, через `dblink` (D-ORDERS-2):

- `orders_history_step` читает следующий диапазон `public.raw_messages.id` архива: по умолчанию 1 000 строк раз в 5 с, при этом архив открыт только на чтение и с ограничением времени запроса.
  - Берутся непересланные карточки ботов (`bots`), то есть сообщения с заголовком `[ДЕПОЗИТ…]` или `[ВЫВОД]`, а также «❌ Заявка #…» и «✅ Депозит принят…».
  - Для каждого сообщения диапазона считается, кто его написал (`orders_history_senders`).
  - Шаг — одна транзакция: если он упал, ничего не меняется, и тот же диапазон повторяется после паузы.
- **Хвост.** Когда первый проход дошёл до конца архива, шаги идут реже (`idle_interval_s`) и читают новые сообщения монитора.
- **Перечитывание.** Раз в `refresh_interval_s` перечитываются ещё открытые карточки последних `refresh_days` дней: итог депозита или вывода бот дописывает правкой уже после чтения.
- **Пользователи и пары** (`orders_history_settle`) — после первого прохода, затем для изменённых карточек:
  - **персонал** — люди, писавшие в группах касс, и пользователи карточек с типом `CASHIER` или `ADMIN`. Они получают роль `casher` в `rm_users`, если у них не было роли или была `guest`/`player`. Роли `support`, `manager`, `admin`, `dev` не меняются никогда (D-ORDERS-4);
  - **игроки** — остальные пользователи карточек: роль `player`, если их нет в `rm_users` или они `guest` (D-ORDERS-5);
  - **пары TGID—MelID** карточек пишутся в `players_links`: у игроков — `active`, у персонала — `staff` (такие пары никого не склеивают). Затем модуль players склеивает их в игроков пачками по 500 (`players_store.heal`);
  - если игрок оказался персоналом (позже нашлось, что он пишет в группе кассы), его связи переводятся в `staff`, и игрок пересчитывается;
  - имена и `@username` карточек пишутся в `players_names`;
  - роли сразу попадают в Directory в памяти.
- Строка подключения к архиву берётся из переменной `AUTOCASH_HISTORY_DSN` или из `settings.ini` монитора (`source_ini`, ключ `[postgres] dsn`). Она читается при старте, хранится только в памяти и никуда не пишется и не выводится.
- Расширение `dblink` ставит суперпользователь, один раз: `.\deploy\windows\autocash-pg.ps1 dblink`. Без него модуль пишет в `logs`, что история не читается, а команды работают.

## Команды

Команды работают в группе `logs` (её ядро иначе не читает, D-ORDERS-6) и в читаемых группах. Права: Dev и Admin.

| Команда | Что показывает |
|---|---|
| `/dev dep mel <MelID> [N]` | депозиты MelID: итог по статусам (сумма успешных — по чеку), последние N (по умолчанию 20, не больше 60) |
| `/dev dep tg <TGID> [N]` | депозиты TGID |
| `/dev dep player <TGID \| MelID \| tg:… \| mel:… \| #игрок> [N]` | депозиты всех TGID и MelID игрока (граф players) |
| `/dev ww mel\|tg\|player … [N]` | то же для выводов |
| `/dev hist` | состояние чтения истории: прочитано, конец первого прохода, сколько заявок, касс, пар, игроков, последняя ошибка |
| `/dev hist pause` / `resume` | остановить / продолжить чтение истории |
| `/dev` | список команд |

Время показывается московское.

## Обратная связь (AGENTS.md, правило 9)

- На `/dev` — ответ автору в тот же чат через Outbox, с антифлудом.
- **Через `delete_after_s` (300 с) ответ и сама команда удаляются** (D-ORDERS-7): в ответе данные игроков.
  - Ответ удаляет аккаунт, который его отправил.
  - Команду сначала пробует удалить аккаунт, который её принял, затем каждый другой аккаунт пула в группе. Удалить чужое сообщение может только админ группы.
  - Если не смог ни один аккаунт, задача удаления закрывается как «не доставлено» (`DELETE_FAILED`), запись уходит в журнал монитора и в `logs`, больше с этой задачей ничего не делается (D-OBX-8).
- Без прав — в чат ничего, отказ в `logs` (D-RM-8).
- В `logs` пишутся:
  - `/dev hist pause|resume` — кто остановил или продолжил чтение;
  - конец первого прохода — сколько выдано ролей `casher` и `player`, сколько новых пар и склеек;
  - новый персонал из хвоста (TGID);
  - история не читается (нет dblink или строки подключения), шаг падает трижды подряд.
- В группы касс и игрокам модуль ничего не пишет.

## Конфигурация

```yaml
modules:
  orders:
    config:
      delete_after_s: 300          # /dev: команда и ответ удаляются через столько секунд (0 — не удалять)
      list_limit: 20               # строк в ответе по умолчанию
      list_max: 60
      staff_user_types: [CASHIER, ADMIN]   # «Тип пользователя» персонала, создающего депозиты за игроков
      history:
        enabled: false             # читать архив Cash Monitor Dev
        source_ini: C:/Users/Den/Documents/ChatGPT/CASH MONITOR DEV/settings.ini   # или AUTOCASH_HISTORY_DSN
        batch: 1000                # строк raw_messages за шаг
        interval_s: 5              # между шагами первого прохода
        idle_interval_s: 30        # между шагами хвоста
        refresh_interval_s: 120    # перечитывание открытых карточек ...
        refresh_days: 3            # ... не старше стольких дней
        settle_interval_s: 120     # роли и пары новых карточек
        statement_timeout_ms: 60000
        bots: [7185799444, 7973286850]   # бот платформы, бот-координатор Полигона
        exclude_tg: []             # служебные аккаунты, которые не пользователи касс
```

Модулю нужны модули `role_manager` и `players`: без них он не стартует.

## Зависимости от ядра и других модулей

- Ядро:
  - `commands_logs_chat` — команды из группы `logs` (`core/gateway/gateway.py`);
  - Outbox: действие `delete`, `delete_after_s`, `not_before_s`, `prefer_account` (`OBX_readme.md`);
  - `Directory.set_users`;
  - `can_run`/`deny`, `render.clip`;
  - таблица `accounts` — аккаунты пула никогда не считаются персоналом или игроками.
- Role Manager: таблицы `rm_users`, `rm_history`.
- Players: `players_links`, `players_names`, `players_store.heal`, `set_state`, `resolve`, `idents`.
- Расширение PostgreSQL `dblink`; архив: `public.raw_messages`, `public.chat_registry` Cash Monitor Dev.
