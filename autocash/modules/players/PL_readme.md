# PL — Players

Модуль узнаёт одного реального человека за многими Telegram-аккаунтами (TGID) и игровыми счетами (MelID).
Решения: `docs/decisions.md`, D-PL-1…D-PL-4.

## Понятия

| | Что это |
|---|---|
| **MelID** | Игровой счёт: на него зачисляются и с него списываются деньги. |
| **TGID** | Telegram-аккаунт, с которого игрок указал MelID. С одним MelID могут работать разные TGID. |
| **Связь** | Одна наблюдённая пара «этот TGID использовал этот MelID» (`pl_links`). Связи не удаляются. |
| **Игрок (PlayerID)** | Связная группа связей: все TGID и MelID, до которых можно дойти по связям (`pl_players`, `pl_nodes`). |

## Как растёт игрок

- **Новая пара, оба идентификатора неизвестны** → новый игрок.
- **Один идентификатор уже у игрока** → второй присоединяется к нему:
  - TGID раньше использовал MelID 123, теперь 321 — это два MelID одного игрока;
  - MelID использовал другой TGID — это два Telegram-аккаунта одного игрока.
- **Идентификаторы у разных игроков** → игроки склеиваются автоматически:
  - остаётся старший (меньший `player_id`);
  - у младшего ставится `merged_into` — старый номер по-прежнему находит игрока (`PL_store.current`, `/player #N`);
  - запись в `pl_journal` (`join`).
- **Порогов размера нет.** Один человек может иметь тысячи MelID и TGID (заказчик: «реальный кейс — 5 200 MelID»).
- **Пара персонала** (роль RM `casher`, `support`, `manager`, `admin`, `dev`, или `Тип пользователя: CASHIER` в карточке) сохраняется со статусом `staff` и ничего не склеивает. Кассиры и поддержка создают депозиты за многих игроков. По истории монитора именно такие аккаунты склеивали сотни чужих MelID.
- **Повтор пары** не меняет ничего, кроме `last_seen`. Время берётся из события, поэтому повтор того же события не меняет ничего вообще.

## Разрыв

`/unlink <TGID> <MelID>` ставит связи статус `disabled`. Игрок пересчитывается по оставшимся активным связям:
- часть с первой связью игрока сохраняет его номер;
- остальные части становятся новыми игроками (`pl_journal`, `split`);
- идентификаторы без единой активной связи уходят из `pl_nodes` (игрока у них нет).

Та же пара, пришедшая снова, разрыв не отменяет. Вернуть связь — `/relink <TGID> <MelID>` (так же включается связь `staff`).

## Откуда приходят пары

- **Сообщения**, у которых сортировщик выделил поля `tgid` и `mel_id`: типы `deposit.*`, `withdrawal.*`, `player.*`.
  Источник связи — `msg:<тип>`, ссылка — `trace_id`. Имена (`username`, `name`) пишутся в `pl_names`.
- **Другие модули** — прямым вызовом `PL_store.add_link(pool, tg_id, mel_id, source=…, ref=…, staff=…)`.
  Autosup так записывает ID, присланный в личке (`source = autosup`).

## Команды

| Команда | Что делает |
|---|---|
| `/player <TGID \| MelID \| tg:… \| mel:… \| #игрок>` | карточка игрока: число и список TGID и MelID (длинный список обрезается), имена, неактивные связи, отметки |
| `/player_deposits <идентификатор> [дней]` | депозиты игрока (если подключён модуль заявок) |
| `/unlink <TGID> <MelID>` | разорвать связь; игрок пересчитывается |
| `/relink <TGID> <MelID>` | восстановить связь (или включить связь персонала) |

- Число без префикса ищется и как TGID, и как MelID. Если оно есть у двух игроков, команда просит уточнить: `tg:…` или `mel:…`.
- Права — через Role Manager (Admin, Dev — всегда).

Обратная связь (AGENTS.md, правило 9):
- на команду — ответ автору в тот же чат;
- `/unlink` и `/relink` — запись в `logs`: `PL: связь TGID … — MelID … разорвана; …; автор …`;
- автоматические склейки в `logs` не пишутся, только в `pl_journal`. Autosup сам сообщает в `logs`, если присланный ID склеил двух игроков.

Действия для правил реакций: `resolve_player` (идентификатор → игрок), `player_mark` (отметка).

## Конфигурация

```yaml
modules:
  players:
    config:
      deposits_days: 30            # период /player_deposits по умолчанию
      staff_user_types: [CASHIER]  # «Тип пользователя» карточки, при котором пара — персонал
      card_links: 40               # сколько неактивных связей показывать в /player
```

Модуль обязателен для Autosup: Autosup не стартует без таблиц `pl_*`.

## Таблицы

| Таблица | Что |
|---|---|
| `pl_links` | связь: `tg_id`, `mel_id`, `state` (active / staff / disabled), `source`, `ref`, `first_seen`, `last_seen`, `changed_by` |
| `pl_nodes` | идентификатор (`kind` tg/mel, `value`) → текущий `player_id`; только идентификаторы активных связей |
| `pl_players` | игрок: `first_link_id`, `merged_into`, `merged_at` |
| `pl_journal` | `join` (склейка), `split` (распад после разрыва), `state` (связь вручную): кто, кого, по какой связи, сколько идентификаторов перешло |
| `pl_names` | имена и username TGID — история |
| `pl_marks` | санкции и отметки (scam, ban, unban …) с автором и временем |

Запись — под одной advisory-блокировкой: склейки не гоняются друг с другом.

При старте модуль доводит до игроков активные связи без игрока (`PL_store.heal`): так строятся игроки из пар, которые миграция перенесла из Autosup и RM. В обычной работе ничего не находит.

## Как другие модули узнают игрока

- В своих таблицах модули хранят TGID и MelID, а не `player_id`: склейки и разрывы тогда применяются к ним сразу.
- Игрок идентификатора — `PL_store.player_of(db, "tg"|"mel", value)`.
- Все MelID человека за TGID — `PL_store.mels_of_tg`; все идентификаторы игрока — `PL_store.idents`.
- Сохранённый ранее `player_id` переводится в текущий через `PL_store.current`.

## Зависимости от ядра и других модулей

- Ядро: `register_action` (правила реакций), `can_run`/`deny` (права), `report` (отчёт `deposits.by_idents`).
- Role Manager: роль пользователя (`directory.user_role`) — для пар персонала.
- Миграция `PL_migrations/001_pl_graph.sql` копирует пары из `as_dialogs` (Autosup) и `rm_player_mel` (RM, D-RM-14), если они есть. RM `004_rm_players_to_pl.sql` после этого удаляет `rm_players`, `rm_player_mel`, `rm_users.player_id`.
