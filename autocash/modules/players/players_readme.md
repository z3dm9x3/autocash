# players — Players

Модуль узнаёт одного реального человека за многими Telegram-аккаунтами (TGID) и игровыми счетами (MelID).
Решения: `docs/decisions.md`, D-PLAYERS-1…D-PLAYERS-5.

В граф попадают только пользователи — роли RM `guest` и `player`. Пары персонала хранятся, но никого не склеивают. Первый выпуск назывался с префиксом `PL` (таблицы `pl_*`). Заказчик попросил писать имя модуля полностью, и миграция переименовала таблицы живой базы вместе с данными (D-PLAYERS-5).

## Понятия

| | Что это |
|---|---|
| **MelID** | Игровой счёт: на него зачисляются и с него списываются деньги. |
| **TGID** | Telegram-аккаунт, с которого игрок указал MelID. С одним MelID могут работать разные TGID. |
| **Связь** | Одна наблюдённая пара «этот TGID использовал этот MelID» (`players_links`). Связи не удаляются. |
| **Игрок (PlayerID)** | Связная группа связей: все TGID и MelID, до которых можно дойти по связям (`players`, `players_nodes`). |

## Как растёт игрок

- **Новая пара, оба идентификатора неизвестны** → новый игрок.
- **Один идентификатор уже у игрока** → второй присоединяется к нему:
  - TGID раньше использовал MelID 123, теперь 321 — это два MelID одного игрока;
  - MelID использовал другой TGID — это два Telegram-аккаунта одного игрока.
- **Идентификаторы у разных игроков** → игроки склеиваются автоматически:
  - остаётся старший (меньший `player_id`);
  - у младшего ставится `merged_into` — старый номер по-прежнему находит игрока (`players_store.current`, `/player #N`);
  - запись в `players_journal` (`join`).
- **Порогов размера нет.** Один человек может иметь тысячи MelID и TGID (заказчик: «реальный кейс — 5 200 MelID»).
- **Пара персонала** (роль RM `casher`, `support`, `manager`, `admin`, `dev`, или `Тип пользователя: CASHIER` / `ADMIN` в карточке) сохраняется со статусом `staff` и ничего не склеивает. Кассиры и поддержка создают депозиты за многих игроков. По истории монитора именно такие аккаунты склеивали сотни чужих MelID.
- **Повтор пары** не меняет ничего, кроме `last_seen`. Время берётся из события, поэтому повтор того же события не меняет ничего вообще.

## Разрыв

`/unlink <TGID> <MelID>` ставит связи статус `disabled`. Игрок пересчитывается по оставшимся активным связям:
- часть с первой связью игрока сохраняет его номер;
- остальные части становятся новыми игроками (`players_journal`, `split`);
- идентификаторы без единой активной связи уходят из `players_nodes` (игрока у них нет).

Та же пара, пришедшая снова, разрыв не отменяет. Вернуть связь — `/relink <TGID> <MelID>` (так же включается связь `staff`).

## Откуда приходят пары

- **Сообщения**, у которых сортировщик выделил поля `tgid` и `mel_id`: типы `deposit.*`, `withdrawal.*`, `player.*`.
  Источник связи — `msg:<тип>`, ссылка — `trace_id`. Имена (`username`, `name`) пишутся в `players_names`.
- **История Cash Monitor Dev** — модуль orders пишет пары карточек архива прямо в `players_links` (источник `history:dep` / `history:ww`) и склеивает их `players_store.heal(pool, limit)` пачками (`orders_readme.md`).
- **Другие модули** — прямым вызовом `players_store.add_link(pool, tg_id, mel_id, source=…, ref=…, staff=…)`.
  Autosup так записывает ID, присланный в личке (`source = autosup`).

## Команды

| Команда | Что делает |
|---|---|
| `/player <TGID \| MelID \| tg:… \| mel:… \| #игрок>` | карточка игрока: число и список TGID и MelID (длинный список обрезается), имена, неактивные связи, отметки |
| `/player_deposits <идентификатор> [дней]` | депозиты игрока (если подключён модуль заявок) |
| `/unlink <TGID> <MelID>` | разорвать связь; игрок пересчитывается |
| `/relink <TGID> <MelID>` | восстановить связь (или включить связь персонала) |

- Число без префикса ищется и как TGID, и как MelID. Если оно есть у двух игроков, команда просит уточнить: `tg:…` или `mel:…`.
- Права — через Role Manager (Admin, Dev — всегда).

Обратная связь (AGENTS.md, правило 9):
- на команду — ответ автору в тот же чат;
- `/unlink` и `/relink` — запись в `logs`: `players: связь TGID … — MelID … разорвана; …; автор …`;
- автоматические склейки в `logs` не пишутся, только в `players_journal`. Autosup сам сообщает в `logs`, если присланный ID склеил двух игроков.

Действия для правил реакций: `resolve_player` (идентификатор → игрок), `player_mark` (отметка).

## Конфигурация

```yaml
modules:
  players:
    config:
      deposits_days: 30            # период /player_deposits по умолчанию
      staff_user_types: [CASHIER, ADMIN]  # «Тип пользователя» карточки, при котором пара — персонал
      card_links: 40               # сколько неактивных связей показывать в /player
```

Модуль обязателен для Autosup: Autosup не стартует без таблиц `players_*`.

## Таблицы

| Таблица | Что |
|---|---|
| `players_links` | связь: `tg_id`, `mel_id`, `state` (active / staff / disabled), `source`, `ref`, `first_seen`, `last_seen`, `changed_by` |
| `players_nodes` | идентификатор (`kind` tg/mel, `value`) → текущий `player_id`; только идентификаторы активных связей |
| `players` | игрок: `first_link_id`, `merged_into`, `merged_at` |
| `players_journal` | `join` (склейка), `split` (распад после разрыва), `state` (связь вручную): кто, кого, по какой связи, сколько идентификаторов перешло |
| `players_names` | имена и username TGID — история |
| `players_marks` | санкции и отметки (scam, ban, unban …) с автором и временем |

Запись — под одной advisory-блокировкой: склейки не гоняются друг с другом.

При старте модуль доводит до игроков активные связи без игрока (`players_store.heal`): так строятся игроки из пар, которые миграция перенесла из Autosup и RM. В обычной работе ничего не находит.

## Как другие модули узнают игрока

- В своих таблицах модули хранят TGID и MelID, а не `player_id`: склейки и разрывы тогда применяются к ним сразу.
- Игрок идентификатора — `players_store.player_of(db, "tg"|"mel", value)`.
- Все MelID человека за TGID — `players_store.mels_of_tg`; все идентификаторы игрока — `players_store.idents`.
- Сохранённый ранее `player_id` переводится в текущий через `players_store.current`.

## Зависимости от ядра и других модулей

- Ядро: `register_action` (правила реакций), `can_run`/`deny` (права), `report` (отчёт `deposits.by_idents`).
- Role Manager: роль пользователя (`directory.user_role`) — для пар персонала.
- Миграция `players_migrations/001_players_graph.sql` копирует пары из `as_dialogs` (Autosup) и `rm_player_mel` (RM, D-RM-14), если они есть. RM `004_rm_players_to_players.sql` после этого удаляет `rm_players`, `rm_player_mel`, `rm_users.player_id`.
