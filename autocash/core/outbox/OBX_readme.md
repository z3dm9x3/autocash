# OBX — Outbox

Единственный компонент, который пишет в Telegram. Модули создают задачи (`OBX_tasks.py`), Outbox их отправляет по своим правилам.
Решения: `docs/decisions.md`, D-OBX-1…D-OBX-5. Outbox — часть ядра (`autocash/core/outbox/`): от него зависят аварийный канал и гарантии после сбоев.

## Как модуль отправляет

| Где | Как |
|---|---|
| при обработке события | `ctx.send(...)` / `ctx.reply(...)` — задача пишется в той же транзакции, что и отметка обработки |
| из протокола или фона | `services.outbox(OutboundDraft(...), "<модуль>")` — с `dedup_key`, повтор не создаёт вторую задачу |

`OutboundDraft`: получатель, текст, правило, вид, приоритет (сейчас у всех 5), `via_account` (привязка к аккаунту), действие (`send` / `pin`), `pin_msg_id`, `pin_after_send`.

## OBX_Antifloodwaiter (`OBX_antiflood.py`)

Нормы Telegram опубликованы только для ботов: не больше 1 сообщения в секунду в один чат, 20 в минуту в группу, около 30 в секунду всего. Для пользовательских аккаунтов норм нет. Берём половину (решение заказчика от 2026-11-18):

| Лимит одного аккаунта | user | bot |
|---|---|---|
| записей в минуту, **равномерно** | 10 (одна в ~6 с) | 900 |
| между записями в один чат | 2 с | 2 с |
| в одну группу в минуту | 10 | 10 |
| случайная добавка к паузе | до 1 с | — |

- Запись — это и отправка, и закрепление.
- Всплесков нет: даже если 500 человек написали одновременно, задачи уходят по одной.
- FloodWait от Telegram ставит аккаунт на паузу поверх этих лимитов.
- Окно восстанавливается после рестарта из `outbound_attempts`.
- Время, которое задача ждала из-за лимита, записывается в `antiflood_wait_ms`.

## OBX_Router (`OBX_router.py`)

- **Привязанная задача** уходит только своим аккаунтом, роутер не участвует. Привязка бывает:
  - `dialog` — личный диалог, отвечает аккаунт, которому написали;
  - `explicit` — аккаунт назвал модуль.
- **Непривязанная задача** (группа, уведомление) уходит аккаунту с наименьшей нагрузкой: записи за минуту плюс задачи в его очереди. При равенстве — аккаунту с обязанностью отправки в этот чат, затем тому, кто дольше не писал. Пример: A — 3, Б — 2, В — 9 → Б.
- В задачу пишутся `router_used` (выбирал ли роутер из нескольких) и `router_load` (нагрузка каждого кандидата).

## OBX_Finalized

- **Подтверждение** — Telegram вернул номер сообщения (`delivered_msg_id`, `confirmed_at`). Прочтение роли не играет.
- **Нет номера за `confirm_timeout_s` (30 с)** — потеряна связь или аккаунт. Тот же аккаунт повторяет отправку с тем же `random_id`; ответ «дубль» значит «уже доставлено», поэтому дублей нет.
- **Окончательный отказ сразу, без повторов**: пользователь заблокировал аккаунт, группы нет, писать запрещено.
- **Аккаунт выпал** (ограничен, бан): непривязанная задача уходит другому аккаунту, привязанная ждёт.
- **Срок задачи** (`ttl_s` по виду: 5 мин / 30 мин / 1 ч / сутки) истёк — финал «не доставлено».
- Каждая окончательная неудача пишется в журнал монитора. В группу `logs` — не чаще раза в 10 минут, со счётчиком.

## Действия

| Действие | Что делает |
|---|---|
| `send` | отправить текст |
| `pin` | закрепить `pin_msg_id` без уведомления, у обоих собеседников личного диалога |
| `send` + `pin_after_send` | после отправки создаётся задача `pin` на отправленное сообщение, привязанная к тому же аккаунту |

## Задача (`outbound_tasks`)

| Поля | Что |
|---|---|
| `id`, `trace_id`, `parent_trace_id` | номер, трасса, трасса события-причины |
| `module`, `rule`, `kind`, `priority` | отправитель-модуль, правило, вид, приоритет |
| `chat_id`, `target_type`, `reply_to` | получатель (user / group) |
| `action`, `text`, `pin_msg_id`, `pin_after_send` | действие |
| `binding`, `dialog_account_id` | привязка к аккаунту (none / dialog / explicit) |
| `account_id`, `router_used`, `router_load` | кто отправил, работал ли роутер, нагрузка кандидатов |
| `stage`, `status`, `reason_code`, `attempts` | этап, статус, причина, попытки |
| `created_at` … `finished_at`, `confirmed_at`, `antiflood_wait_ms` | время этапов, подтверждение, ожидание антифлуда |
| `random_id`, `delivered_msg_id` | защита от дублей, номер в Telegram |

Журналы:
- `outbound_attempts` — каждая попытка: аккаунт, результат (`delivered`, `duplicate`, `pinned`, `error`, `flood_wait`), код ошибки;
- `outbound_tasks` — журнал отправленных сообщений;
- трасса задачи — `/trace`.
