# OBX — Outbox

Единственный компонент, который пишет в Telegram. Модули создают задачи (`OBX_tasks.py`), Outbox их отправляет по своим правилам.
Решения: `docs/decisions.md`, D-OBX-1…D-OBX-8. Outbox — часть ядра (`autocash/core/outbox/`): от него зависят аварийный канал и гарантии после сбоев.

## Как модуль отправляет

| Где | Как |
|---|---|
| при обработке события | `ctx.send(...)` / `ctx.reply(...)` — задача пишется в той же транзакции, что и отметка обработки |
| из протокола или фона | `services.outbox(OutboundDraft(...), "<модуль>")` — с `dedup_key`, повтор не создаёт вторую задачу |

`OutboundDraft`: получатель, текст, правило, вид, приоритет (сейчас у всех 5), `via_account` (привязка к аккаунту), действие (`send` / `pin` / `delete`), `pin_msg_id`, `pin_after_send`, `target_msg_id` (что удалить), `not_before_s` (не раньше чем через столько секунд), `delete_after_s` (удалить отправленное через столько секунд), `prefer_account` (у непривязанной задачи — какой аккаунт пробовать первым).

## Лимиты аккаунта (D-OBX-7)

У каждого аккаунта свои лимиты, два отдельных бюджета:

| Бюджет | Что входит | Лимит |
|---|---|---|
| записи | отправка, закрепление, удаление | 20 в минуту, равномерно (раз в ~3 с); 1 в 2 с в один чат; 10 в минуту в одну группу |
| чтения | любой другой вызов Telegram: история, диалоги, догон групп, перечитывание, поиск собеседника | 20 в минуту, равномерно (раз в 3 с) |

Для ботов так же. Флудвейт по документации Telegram может прийти на любой метод, поэтому считаются все вызовы.

**Предохранитель (`OBX_fuse.py`).** Первый FloodWait на аккаунте — оба его лимита вдвое (10 и 10), сообщение в `logs`. Следующие FloodWait лимиты не режут: пауза на время Telegram. Сниженные лимиты хранятся в базе (`obx_account_limits`), переживают рестарт и возвращаются только вручную.

| Команда (Admin, Dev, группа tech) | Что делает |
|---|---|
| `/obx` | лимиты и нагрузка каждого аккаунта за минуту, отметка «СНИЖЕНЫ» |
| `/obx reset <ID аккаунта \| all>` | вернуть полные лимиты; запись в `logs` |

**Как чтения проходят через Outbox.** Каждый вызов Telegram идёт через лимитер аккаунта; перед ним Outbox пропускает чтение через бюджет чтений этого аккаунта («ворота»), не занимая место в очереди вызовов. Аккаунт для чтения группы выбирает роутер чтений: наименее загруженный по чтениям, при равенстве — тот, у кого обязанность чтения. Подтверждения для чтений пока нет.

## OBX_Antifloodwaiter (`OBX_antiflood.py`)

Нормы Telegram опубликованы только для ботов: не больше 1 сообщения в секунду в один чат, 20 в минуту в группу, около 30 в секунду всего. Для пользовательских аккаунтов норм нет; лимиты заданы заказчиком по замеру на аккаунте Dmitry (D-OBX-7), бюджеты — выше в «Лимиты аккаунта».

- Запись — это отправка, закрепление и удаление.
- Всплесков нет: даже если 500 человек написали одновременно, задачи уходят по одной.
- FloodWait от Telegram ставит аккаунт на паузу поверх этих лимитов.
- Окно восстанавливается после рестарта из `outbound_attempts`.
- Время, которое задача ждала из-за лимита, записывается в `antiflood_wait_ms`.

## OBX_Router (`OBX_router.py`)

- **Привязанная задача** уходит только своим аккаунтом, роутер не участвует. Привязка бывает:
  - `dialog` — личный диалог, отвечает аккаунт, которому написали;
  - `explicit` — аккаунт назвал модуль.
- **Непривязанная задача** (группа, уведомление) уходит аккаунту с наименьшей нагрузкой: записи за минуту плюс задачи в его очереди. При равенстве — аккаунту с обязанностью отправки в этот чат, затем тому, кто дольше не писал. Пример: A — 3, Б — 2, В — 9 → Б.
- В задачу пишутся `router_used` (выбирал ли роутер из нескольких) и `router_load` (нагрузка каждого кандидата).

## OBX_Finalized

- **Подтверждение** — Telegram вернул номер сообщения (`delivered_msg_id`, `confirmed_at`). Прочтение роли не играет.
- **Нет номера за `confirm_timeout_s` (30 с)** — потеряна связь или аккаунт. Тот же аккаунт повторяет отправку с тем же `random_id`; ответ «дубль» значит «уже доставлено», поэтому дублей нет.
- **Окончательный отказ сразу, без повторов**: пользователь заблокировал аккаунт, группы нет, писать запрещено.
- **Аккаунт выпал** (ограничен, бан): непривязанная задача уходит другому аккаунту, привязанная ждёт.
- **Срок задачи** (`ttl_s` по виду: 5 мин / 30 мин / 1 ч / сутки) истёк — финал «не доставлено».
- Каждая окончательная неудача пишется в журнал монитора. В группу `logs` — не чаще раза в 10 минут, со счётчиком.

## Действия

| Действие | Что делает |
|---|---|
| `send` | отправить текст |
| `pin` | закрепить `pin_msg_id` без уведомления, у обоих собеседников личного диалога |
| `send` + `pin_after_send` | после отправки создаётся задача `pin` на отправленное сообщение, привязанная к тому же аккаунту |
| `delete` | удалить `target_msg_id` у всех (D-OBX-8) |
| `send` + `delete_after_s` | после отправки создаётся задача `delete` отправленного сообщения: не раньше чем через `delete_after_s`, первым пробует отправивший аккаунт |

**Удаление (D-OBX-8).**
- Сначала пробует `prefer_account` (обычно аккаунт, который отправил или принял сообщение), затем каждый другой аккаунт пула в этом чате, наименее загруженный первым.
- Своё сообщение аккаунт удаляет всегда, чужое — только если он админ группы.
- Аккаунт, которому Telegram отказал (`MESSAGE_DELETE_FORBIDDEN` и т. п.) или который ничего не удалил, для этой задачи больше не пробует. Попытка пишется в `outbound_attempts` с результатом `not_deleted`, поэтому список попробовавших переживает рестарт.
- Если не смог ни один аккаунт, задача заканчивается `not_delivered` / `DELETE_FAILED`. Запись уходит в журнал монитора и в группу `logs`, даже если сообщение было в самой `logs`. Больше с задачей ничего не делается.
- FloodWait — пауза, как у отправки; сетевая ошибка — повтор тем же аккаунтом.

**Задача по времени (`not_before`).** Задача не уходит к роутеру раньше своего времени и ждёт со статусом `waiting` / `SCHEDULED`. Её срок жизни отсчитывается от `not_before`.

## Задача (`outbound_tasks`)

| Поля | Что |
|---|---|
| `id`, `trace_id`, `parent_trace_id` | номер, трасса, трасса события-причины |
| `module`, `rule`, `kind`, `priority` | отправитель-модуль, правило, вид, приоритет |
| `chat_id`, `target_type`, `reply_to` | получатель (user / group) |
| `action`, `text`, `pin_msg_id`, `pin_after_send`, `target_msg_id`, `delete_after_s` | действие |
| `not_before`, `prefer_account_id` | не раньше; кого пробовать первым (удаление) |
| `binding`, `dialog_account_id` | привязка к аккаунту (none / dialog / explicit) |
| `account_id`, `router_used`, `router_load` | кто отправил, работал ли роутер, нагрузка кандидатов |
| `stage`, `status`, `reason_code`, `attempts` | этап, статус, причина, попытки |
| `created_at` … `finished_at`, `confirmed_at`, `antiflood_wait_ms` | время этапов, подтверждение, ожидание антифлуда |
| `random_id`, `delivered_msg_id` | защита от дублей, номер в Telegram |

Журналы:
- `outbound_attempts` — каждая попытка: аккаунт, результат (`delivered`, `duplicate`, `pinned`, `deleted`, `not_deleted`, `error`, `flood_wait`), код ошибки;
- `outbound_tasks` — журнал отправленных сообщений;
- трасса задачи — `/trace`.
