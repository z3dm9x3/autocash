# Autocash — постоянный контекст проекта

> Этот файл лежит в корне репозитория как `AGENTS.md`; `CLAUDE.md` импортирует его. Он действует на всех этапах. Задачи этапов приходят отдельными промтами `01…07`. Полное ТЗ лежит в `docs/TZ.md`; номера требований (ФТ-x.y, НФТ-n, А-n, П-n) ссылаются на него. Если промт этапа и ТЗ расходятся, прав ТЗ.

## Роль

Ты ведущий Python-разработчик и строишь **Autocash**, обработчик сообщений Telegram. Пиши production-код: асинхронный, идемпотентный, с тестами, без «магии» и скрытых допущений.

## Что делает система

Пул из 1–10 аккаунтов Telegram (пользовательские MTProto и боты) принимает сообщения примерно из 100 групп-касс, личных диалогов игроков, рабочих и служебных групп. Каждое сообщение сохраняется, раскладывается по типам и передаётся модулям. Модули ведут сущности (заявки, игроки и др.), считают статистику и отправляют сообщения по правилам. Каждую задачу видно от поступления до финального статуса.

Вне объёма: кассы-исключения с уникальной логикой, содержимое каналов.

## Принципы (не нарушать)

- **П-1. Всеядность.** Ядро знает только сообщения, признаки и задачи. Заявки, депозиты, тикеты и промокоды принадлежат модулям, и в ядре не должно быть ни одного `if deposit`.
- **П-2. Конструктор.** В коде живут фундаментальные действия. Тексты-триггеры, шаблоны разбора, правила и тексты ответов задаются в YAML-конфиге.
- **П-3. Три слоя смысла.** Extractor описывает, *что есть* в тексте (формы). Сортировщик определяет *тип* сообщения и смысл полей. Модуль решает, *что делать*.
- **П-4. Изоляция.** У каждого модуля и каждого аккаунта своя очередь и свои ресурсы. Сбой одного не тормозит остальных.
- **П-5. Динамический пул.** Система работает при любом числе аккаунтов от 1 до 10 и перестраивает обязанности при любом изменении пула, в том числе внеплановом.
- **П-6. Наблюдаемость.** У каждой задачи в любой момент есть этап и статус, записанные в БД.
- **П-7. Монолит.** Одно приложение, модули — его пакеты. Никаких микросервисов и брокеров сообщений.

## Архитектура

```
Gateway → Extractor → SQLite (буфер) → Uploader → PostgreSQL → Сортировщик → Менеджер очереди → Модули → Вывод
```

| Этап | Вход | Выход |
|---|---|---|
| Gateway | события Telegram от всех аккаунтов | сырое событие + аккаунт + trace_id |
| Extractor | сырое событие | метаданные, нормализованный текст, признаки |
| SQLite | запись Extractor | надёжно сохранённая запись |
| Uploader | записи SQLite | пачка, зафиксированная в PostgreSQL |
| PostgreSQL | пачки, данные модулей, трассы | постоянное хранилище |
| Сортировщик | зафиксированная пачка | сообщения с типом и именованными полями |
| Менеджер очереди | рассортированные сообщения | задачи в очередях модулей |
| Модули | задачи | изменения сущностей, исходящие задачи |
| Вывод | исходящие задачи | доставлено / финальный статус с причиной |

Единственное исключение из цепочки — аварийный канал (НФТ-18): `/status`, `/accounts` и тревоги обслуживает Gateway напрямую, и они работают без PostgreSQL.

### Условия скорости (обязательны, PostgreSQL на основном пути)

- **А-1.** Uploader пишет в PG пачками, одна транзакция на пачку. Пачка уходит по таймеру (цель ≤ 100 мс, конфиг) или по числу записей, что наступит раньше.
- **А-2.** После коммита Uploader передаёт пачку сортировщику **в памяти**. Из PG сортировщик читает только при восстановлении, со своей отметки.
- **А-3.** Очереди модулей живут в памяти. PG хранит данные, трассы и отметки обработки.
- **А-4.** Модули пишут результаты через общий пакетный писатель.
- **А-5.** Extractor помечает команды. Uploader отправляет пачку с командой сразу, менеджер очереди ставит её в верхнюю полосу.
- **А-6.** SQLite: `journal_mode=WAL`, `synchronous=FULL`, запись пачками, вызовы в отдельном потоке. Event loop не блокируется.
- **А-7.** Тяжёлое — вне event loop: regex из конфига через `re2` (или с таймаутом), нечёткий поиск и тяжёлые отчёты в отдельном процессе.
- **А-8.** На пути обработки входящего нет вызовов Telegram API. Используются только данные самого update и кеш сущностей.

## Стек и окружение (НФТ-1…3)

- Python 3.12+, asyncio, **Telethon** (и для ботов), PostgreSQL 16+, SQLite (WAL), YAML + pydantic, Jinja2 (sandbox), re2.
- Железо: 2 ядра × 2 ГГц, 8 ГБ ОЗУ, SSD. Это ограничение, а не пожелание: не тащи тяжёлые зависимости.
- ОС: Ubuntu и второй дистрибутив Linux (пока не выбран). Запуск через systemd с `WatchdogSec`.
- Рекомендации (можно заменить, зафиксировав решение): `asyncpg`, Alembic или версионированные SQL-миграции, `pytest` + `pytest-asyncio`, `ruff`, `mypy`.

## Глоссарий

- **Аккаунт** — user-аккаунт или бот, подключённый к Системе. **Пул** — все подключённые аккаунты (1–10).
- **Источник** — чат. **Пользователи, группы, роли и права** ведёт модуль Role Manager в PostgreSQL (таблицы `rm_*`, D-RM-7). Роли пользователей: guest, player, casher, support, manager, admin, dev; групп: other (известна, не читается — по умолчанию), tech, dop, ww (читаются). Права — только у пользователей. Старые роли из ТЗ (`kassa`, …) остаются в разделе `sources` до переделки.
- **Покрытие чата** — число аккаунтов пула в состоянии active/paused/restricted, состоящих в чате.
- **Событие** — новое сообщение, правка, удаление, команда или таймер. **Задача** — входящее событие или исходящее сообщение. **Трасса** — история этапов задачи с отметками времени. **Код причины** — стандартный код ожидания или неуспешного финала.
- **Признак** — фрагмент текста заданной формы. **Манифест** — описание форм признаков для Extractor.
- **Тип сообщения** — метка сортировщика (`deposit.request`, `unknown`). **Шаблон** — набор правил сортировки для типового источника.
- **Модуль** — код, который знает смысл своих типов и ведёт свои сущности. **Правило** — «когда — если — то». **Действие** — фундаментальная операция ядра.
- **TGID** — Telegram user id («ID» в заявке). **MelID** — номер игрового счёта («Номер счёта»). **Deposit ID** — ключ заявки, общий для всех касс.

## Инварианты надёжности

1. Событие считается принятым, когда оно закоммичено в SQLite. Каждое такое событие обрабатывается после любого сбоя (НФТ-9).
2. Любая повторная обработка даёт тот же результат: upsert по `(аккаунт, chat_id, msg_id, версия)`, уникальный ключ исходящей задачи «событие + правило».
3. `random_id` генерируется и сохраняется **до** отправки. `RANDOM_ID_DUPLICATE` означает «доставлено».
4. Состояние диалога пишется в БД **до** отправки ответа.
5. Переходы в «ожидает», «отправка» и финальные статусы пишутся синхронно, промежуточные этапы — пакетным писателем.
6. `flood_sleep_threshold=0`. FloodWait обрабатывает наш лимитер, а не библиотека.
7. Все отметки времени в UTC. Часовой пояс границ суток для отчётов задаётся в конфиге.
8. Номера карт и телефонов хранятся как есть, без маскировки (решение заказчика от 2026-11-17, D-RM-5). Защита — доступ к серверу и БД; текст сообщений удаляется по сроку из конфига.
9. Файлы сессий хранятся вне git, зашифрованными, доступны только системному пользователю сервиса, одна сессия — один процесс.

## Нефункциональные цели

| | Значение |
|---|---|
| Нагрузка | 5–10 тыс. сообщений/сутки сейчас; рост ×10 без смены архитектуры |
| Ответ на команду чтения | ≤ 1 с |
| Приём → начало обработки модулем | ≤ 1 с в живом потоке |
| Сопоставление и статистика | ≤ несколько секунд |
| Backfill | не нарушает две строки выше |
| Отчёты | отдельный пул соединений со `statement_timeout`, по агрегатам; запись пачек не страдает |

## Правила работы

1. **Начинай этап с плана**: пакеты и файлы, таблицы и миграции, интерфейсы, перечень тестов с привязкой к критериям приёмки. Покажи план и сразу приступай к коду: подтверждения ждать не нужно (решение заказчика от 2026-11-14). Развилки решай рекомендованными дефолтами и записывай в `docs/decisions.md`.
2. **Telegram — за интерфейсом.** Код ядра зависит от абстракции клиента, а не от Telethon напрямую. Для тестов сделай фейковый Telegram, который умеет push-обновления, `getChannelDifference`, FloodWait, PEER_FLOOD, бан, исключение из чата и «difference too long». Реальные аккаунты в автотестах запрещены.
3. **Открытые вопросы ТЗ (раздел 8) не зашивай в код.** Каждое такое значение делай параметром конфига с разумным дефолтом и комментарием `# OPEN-QUESTION: <ссылка на требование>`. Сводку дефолтов веди в `docs/open_questions.md`.
4. **Неясность или противоречие в ТЗ** не решай молча. Мелкое — выбери вариант и запиши в `docs/decisions.md` (что, почему, альтернатива). Блокирующее — остановись и спроси.
5. **Держись рамок этапа.** Не реализуй следующие этапы заранее, но оставляй точки расширения, которые они потребуют.
6. **Тесты** всегда со сроками: один тест — не дольше 5 минут (`timeout` в `pyproject.toml`, дольше — только явной меткой `@pytest.mark.timeout`), весь прогон — внешним ограничением, например `timeout 2400 python -m pytest`. Долгий прогон — в фоне, работа продолжается параллельно; ждать тесты часами нельзя (решение заказчика от 2026-11-16). PostgreSQL — настоящий (docker compose или testcontainers), SQLite — настоящий файл. Регрессионные фикстуры из реальных сообщений лежат в `tests/fixtures/messages/` (НФТ-21). Форматы сообщений не выдумывай: если фикстур не хватает, попроси образцы.
7. **Definition of Done этапа**: все тесты зелёные, `ruff` и `mypy` чистые, каждый критерий приёмки покрыт тестом (таблица «критерий → тест» в `docs/acceptance/<этап>.md`), обновлены `docs/open_questions.md` и `docs/decisions.md`, конфиг-примеры проходят схему.
8. Архитектурные развилки в ТЗ решены в пользу «вариантов А». Следуй тексту ТЗ как написано.
9. **Обратная связь от команд ограничивается тщательно.** Аккаунты пула — пользовательские: каждое лишнее сообщение в группе заметно кассирам и игрокам и тратит лимиты Telegram. Правила:
   - на нашу команду всегда есть ответ — тому, кто её дал, в чат, где её дали (если для команды явно не указано иное);
   - команда без прав: в чат ничего; отказ — в группу `logs` (не чаще раза на пользователя в 10 минут) и в журнал монитора (D-RM-8);
   - на чужие команды (`/start` и любые, которых нет у модулей) не реагируем вовсе;
   - побочные эффекты команды (выдана роль, изменён конфиг, применена санкция) пишутся в группу `logs`;
   - в затронутую группу или чат сообщение о побочном эффекте НЕ отправляется («группе установлена роль» и подобное запрещено);
   - любое сообщение модуля в чат, кроме ответа на команду и записи в `logs`, должно быть описано в readme модуля.
10. **В Telegram пишет только Outbox** (`autocash/core/outbox/`, `OBX_readme.md`). Модули создают задачи: `ctx.send`/`ctx.reply` при обработке события, `services.outbox` вне его. Отправка, закрепление и любые другие записи идут через Outbox с его лимитами (OBX_Antifloodwaiter), выбором аккаунта (OBX_Router) и подтверждением (OBX_Finalized).
11. **Модули.** Каждый модуль — своя папка `autocash/modules/<имя>/` с коротким префиксом (Role Manager — `RM`):
   - файлы модуля называются `<ПРЕФИКС>_…` (`RM_module.py`, `RM_ids.py`); исключения — только служебные имена Python (`__init__.py`, `conftest.py`);
   - документация модуля — `<ПРЕФИКС>_readme.md` в его папке: команды, конфиг, что пишет и куда, обратная связь;
   - тесты модуля — в его папке, `<ПРЕФИКС>_tests/<ПРЕФИКС>_test_*.py`;
   - всё о модуле лежит в его папке; исключения — явные зависимости от ядра, их перечисляет readme модуля;
   - поиск всего, что относится к модулю: `rg -l RM_` или по префиксу в именах файлов.
