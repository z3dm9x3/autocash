# Решения по неясностям ТЗ

Формат: что решено, почему, какая была альтернатива. Нумерация `D-<этап>-<n>`.

## Этап 1a

### D-1a-1. Номер версии сообщения
**Что.** `version = 0` для нового сообщения, для правки — unix-время `edit_date`.
**Почему.** ФТ-2.2 требует upsert по `chat_id + msg_id + edit_date`, ФТ-4.4 — по `(аккаунт, chat_id, msg_id, версия)`. Версия, вычисляемая из самого обновления, одинакова у всех аккаунтов пула и при повторной выгрузке, поэтому не нужен счётчик в БД и обращение к ней на пути приёма (А-8).
**Альтернатива.** Порядковый номер 1, 2, 3… — требует чтения из PostgreSQL до записи в буфер.
**Следствие.** Две правки с разным текстом в одну и ту же секунду дадут одну версию (сохранится первая). Telegram отдаёт `edit_date` с точностью до секунды, точнее различить нельзя.

### D-1a-2. Ключ дедупликации и поле `scope_id`
**Что.** В ключе сообщения вместо «аккаунта» стоит `scope_id`: `0` для супергрупп и каналов (номер сообщения общий для всех аккаунтов), id аккаунта — для личных диалогов и обычных групп (номера у каждого аккаунта свои). Отметки «видел» по аккаунтам лежат в `message_seen`.
**Почему.** Так выполняются одновременно ФТ-2.2 («сохраняется первая запись, остальным — отметка „видел“») и ФТ-4.4 (upsert по аккаунту): для касс ключ не зависит от аккаунта, для остальных чатов зависит.
**Альтернатива.** Всегда хранить аккаунт в ключе и схлопывать дубли отдельным шагом — лишняя запись на каждое сообщение каждой кассы.

### D-1a-3. Сообщение без текстовых изменений не создаёт версию
**Что.** Правка, после которой хеш нормализованного текста совпал с предыдущим (изменилась только разметка, кнопки, реакции), отбрасывается на Gateway.
**Почему.** ФТ-5.2: новая версия сохраняется при изменении текста.
**Следствие.** Память о последнем хеше — в процессе (50 000 сообщений). После рестарта первая такая правка всё же создаст версию-дубль по тексту; на корректность обработки это не влияет.

### D-1a-4. Результат сортировки фиксируется до передачи модулям
**Что.** Сортировщик дожидается коммита типа и полей в PostgreSQL и только потом раздаёт сообщения в очереди модулей. Очередь модуля — окно над PostgreSQL: если она переполнена, сообщение не держится в памяти и не блокирует сортировщик, а перечитывается из базы позже.
**Почему.** Очередь модуля можно в любой момент пересобрать из PostgreSQL (ФТ-7.7, п. 3.4), а медленный модуль не тормозит остальные (П-4).
**Альтернатива.** Раздавать сразу, писать через пакетный писатель без ожидания (буквальное прочтение ФТ-6.5) — быстрее на один проход писателя (~20 мс), но после сбоя модуль мог бы обработать сообщение, тип которого не сохранён.

### D-1a-5. Темп потока в приёмочном тесте критерия 1
**Что.** Критерий 1 («p95 ≤ 1 с на прогоне 1000 сообщений») проверяется на потоке 50 сообщений в секунду.
**Почему.** Промт этапа темп не задаёт. НФТ-4 с десятикратным ростом — 100 тыс. сообщений в сутки, то есть ~1,2 в секунду в среднем; 50/с — запас примерно в 40 раз.
**Измерено** на машине разработки (Windows, 8 логических ядер), один процесс:

| Поток | p50 | p95 |
|---|---|---|
| 25/с | 0,09 с | 0,14 с |
| 50/с | 0,11 с | 0,25–0,40 с |
| 100/с | 0,21 с | 0,93 с |
| 200/с | 3,4 с | 5,6 с — конвейер не успевает |

**Ограничение.** Потолок — около 100–150 сообщений в секунду: конвейер упирается в CPU одного ядра. Самая дорогая часть — Extractor, ~2,4 мс на сообщение (обёртка `google-re2` написана на Python). На целевом железе (2 × 2 ГГц) потолок будет ниже; его нужно измерить там.
**Альтернатива, если понадобится больше.** Вынести извлечение в отдельный процесс (в духе А-7) — задействует второе ядро. Сейчас не сделано: усложняет порядок приёма и горячую перезагрузку манифеста, а запас к требуемой нагрузке большой.

### D-1a-6. Лимит параллельности модуля ограничивает `handle()`, а не ожидание коммита
**Что.** Воркер модуля после `handle()` сразу берёт следующее событие; запись результата ждёт отдельная задача. Ключ упорядочения остаётся занятым до коммита (ФТ-7.5), число событий, одновременно ждущих коммита, ограничено `queue.commit_window` (500).
**Почему.** Иначе за один проход пакетного писателя (А-4) фиксируется не больше «лимит параллельности» событий — ~200 событий/с при лимите 16.
**Альтернатива.** Поднять лимит параллельности — но он задан модулем ради его собственной нагрузки на базу (ФТ-8.1).

### D-1a-7. Неожиданная ошибка не останавливает пакетный писатель
**Что.** Любое исключение (включая «протёкшую» отмену), вышедшее из записи пачки, логируется как CRITICAL с трассировкой, пачка возвращается в голову очереди и повторяется. Ожидание PostgreSQL (`wait_available`) считает нераспознанную ошибку подключения недоступностью базы, а не поводом упасть.
**Почему.** При остановке PostgreSQL задача писателя дважды на ~45 прогонов теста молча завершалась, и все синхронные записи (инвариант 5) ждали вечно. Точную ошибку поймать не удалось — после исправления она не повторилась; если повторится, попадёт в лог.
**Альтернатива.** Завершать процесс и полагаться на перезапуск systemd — рабочий вариант для этапа 1c (watchdog, НФТ-16), но терять процесс из-за сбоя одной пачки незачем.

### D-1a-8. Сообщения пула: `origin=system` определяется по тексту
**Что.** Сообщение от аккаунта пула считается отправленным Системой (`origin=system`), если его текст совпал с текстом, который Вывод отправлял в этот чат за последние 120 с; иначе `origin=human`.
**Почему.** На пути приёма нельзя обращаться к PostgreSQL за `msg_id` исходящей задачи (А-8), а push-обновление о своём сообщении может прийти раньше, чем вернётся ответ на отправку.
**Следствие.** Если сотрудник вручную отправит в тот же чат точно такой же текст в течение двух минут после автоответа, его сообщение будет помечено `system`. На этапе 1b, когда отправкой займётся пул, сверку стоит дополнить `msg_id` доставленной задачи.

### D-1a-9. Модуль demo не подключается по умолчанию
**Что.** `python -m autocash.cli.run` регистрирует демонстрационный модуль, только если в конфиге есть раздел `modules.demo`.
**Почему.** Модуль отвечает «pong» на `/ping` — в реальных кассах это была бы отправка сообщений, о которой никто не просил.

### D-1a-10. PostgreSQL в тестах — временный кластер вместо docker
**Что.** Тесты поднимают собственный кластер (`initdb` + `pg_ctl`) во временном каталоге на свободном порту; бинарники ищутся в `AUTOCASH_PG_BIN`, `PATH`, стандартных каталогах установки.
**Почему.** На машине разработки нет Docker; при этом нужен настоящий PostgreSQL, который тест может остановить и запустить (критерий 3). Установленные на машине базы не затрагиваются.
**Альтернатива.** docker compose / testcontainers — можно добавить для CI, тесты от способа запуска не зависят.
