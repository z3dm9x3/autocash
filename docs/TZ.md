# ТЗ: Autocash — обработчик сообщений Telegram

## 1. Общие сведения

1.1. Наименование: Autocash — обработчик сообщений Telegram (далее — Система).

1.2. Назначение. Система принимает сообщения из пула аккаунтов Telegram, сохраняет их, раскладывает по типам и передаёт модулям. Модули ведут данные (заявки, игроки, тикеты, промокоды, отчёты и др.), считают статистику и отправляют сообщения по правилам. Каждая задача отслеживается от поступления до финального статуса.

1.3. Область применения:
- около 100 групп-касс с типовыми сообщениями бота и кассиров;
- личные сообщения игроков;
- рабочие группы сотрудников;
- служебные группы логов.

Кассы-исключения с уникальной логикой и содержимое каналов войдут в следующие версии.

1.4. Термины

| Термин | Значение |
|---|---|
| Аккаунт | пользовательский аккаунт или бот Telegram, подключённый к Системе |
| Пул аккаунтов | все подключённые аккаунты, от 1 до 10; состав меняется во время работы |
| Источник | чат (группа, личный диалог, канал), из которого приходят сообщения |
| Роль источника | метка чата (kassa, dop, ww, tech, info, logs, debug, channel и др.), определяющая правила обработки |
| Покрытие чата | число активных аккаунтов пула, состоящих в чате |
| Событие | новое сообщение, правка, удаление, команда или срабатывание таймера |
| Задача | единица работы Системы: входящее событие или исходящее сообщение |
| Трасса | история этапов задачи с отметками времени |
| Код причины | стандартный код, объясняющий ожидание или неуспешный финал задачи |
| Признак | фрагмент текста заданной формы (число, сумма, слово, пара «метка: значение») |
| Манифест | файл с описанием форм признаков для Extractor |
| Тип сообщения | метка, которую присваивает сортировщик (например, deposit.request, unknown) |
| Шаблон | набор правил сортировки для типового источника (например, стандартной кассы) |
| Модуль | часть кода, которая знает смысл своих типов сообщений и ведёт свои сущности |
| Правило | конфигурируемая связка «когда — если — то», запускающая действия |
| Действие | фундаментальная операция в коде: найти, связать, сохранить, отправить по шаблону и др. |
| TGID | идентификатор пользователя Telegram («ID» в заявке) |
| MelID | номер игрового счёта («Номер счёта» в заявке) |

## 2. Цели и принципы построения

### 2.1. Цели

1. Собирать все сообщения из чатов пула в одну базу сразу после их появления.
2. Автоматически вести заявки, игроков и другие сущности и считать по ним статистику.
3. Автоматизировать часть ответов и действий; сотрудники при этом продолжают писать с тех же аккаунтов вручную.
4. Менять триггеры и логику реакций через конфигурацию.
5. Показывать по каждой задаче, на каком она этапе, сколько на нём находится и чем закончилась.

### 2.2. Принципы

- **П-1. Всеядность.** Ядро работает с сообщениями, признаками и задачами. Предметные сущности — заявка, депозит, вывод, тикет, промокод — принадлежат модулям.
- **П-2. Конструктор.** Код содержит фундаментальные действия. Тексты-триггеры, шаблоны разбора, правила и тексты ответов задаются конфигурацией.
- **П-3. Три слоя смысла.** Extractor описывает, что есть в тексте. Сортировщик определяет тип сообщения. Модуль решает, что с ним делать.
- **П-4. Изоляция.** У каждого модуля и каждого аккаунта своя очередь и свои ресурсы; задержка одного из них затрагивает только его самого.
- **П-5. Динамический пул.** Система работает с любым числом аккаунтов от 1 до 10 и перестраивает распределение обязанностей при каждом изменении пула, в том числе внеплановом.
- **П-6. Наблюдаемость.** У каждой задачи в любой момент есть этап и статус, записанные в БД.
- **П-7. Монолит.** Одно приложение, модули — его части.

## 3. Архитектура

3.1. Событие проходит цепочку: Gateway → Extractor → SQLite (резервный буфер) → Uploader → PostgreSQL → Сортировщик → Менеджер очереди → Модули → Вывод.

Справа от этапов — условия скорости из п. 3.2. Ключевое из них — передача пачки от PostgreSQL к сортировщику в памяти приложения.

| № | Этап | Вход | Выход |
|---|---|---|---|
| 1 | Gateway | события Telegram от всех аккаунтов пула | сырое событие с отметкой аккаунта и trace_id |
| 2 | Extractor | сырое событие | метаданные, нормализованный текст, признаки |
| 3 | SQLite | запись Extractor | надёжно сохранённая запись |
| 4 | Uploader | записи SQLite | пачка, зафиксированная в PostgreSQL |
| 5 | PostgreSQL | пачки Uploader, данные модулей, трассы | постоянное хранилище, отчёты |
| 6 | Сортировщик | зафиксированная пачка | сообщения с типом и именованными полями |
| 7 | Менеджер очереди | рассортированные сообщения | задачи в очередях модулей |
| 8 | Модули | задачи | изменения сущностей, исходящие задачи |
| 9 | Вывод | исходящие задачи | доставленные сообщения или финальный статус с причиной |

3.2. Условия скорости. PostgreSQL находится на основном пути, поэтому цепочка выполняет следующие условия:

- **А-1.** Uploader пишет в PostgreSQL пачками, одной транзакцией на пачку. Пачка уходит по таймеру или по числу записей, что наступит раньше. Интервал задаётся в конфиге, целевое значение — до 100 мс.
- **А-2.** После фиксации пачки Uploader передаёт её сортировщику в памяти приложения. Из PostgreSQL сортировщик читает при восстановлении после рестарта, начиная со своей отметки.
- **А-3.** Очереди модулей находятся в памяти приложения. PostgreSQL хранит данные, трассы и отметки обработки.
- **А-4.** Модули пишут результаты в PostgreSQL через общий пакетный писатель.
- **А-5.** Extractor помечает команды. Uploader отправляет пачку с командой сразу, менеджер очереди ставит команду в верхнюю полосу.
- **А-6.** SQLite работает в режиме WAL с synchronous=FULL и пишет пачками. Вызовы SQLite выполняются в отдельном потоке, основной цикл событий продолжает приём во время записи на диск.
- **А-7.** Тяжёлые операции выполняются вне основного цикла событий: регулярные выражения из конфигурации — движком re2 или с таймаутом, нечёткий поиск и тяжёлые отчёты — в отдельном процессе.
- **А-8.** Обработка входящего сообщения использует данные самого обновления и кеш сущностей; вызовы Telegram API в этом пути отсутствуют.

3.3. Недоступность PostgreSQL. Приём и запись в SQLite продолжаются, сортировка и модули ждут восстановления базы, задачи получают статус ожидания с кодом DB_UNAVAILABLE. После восстановления Uploader выгружает накопленное в порядке поступления, и обработка догоняет поток. Команда /status и тревоги работают и в это время (НФТ-18).

3.4. Жёсткая перезагрузка сервера

| Компонент | Состояние после перезагрузки | Восстановление |
|---|---|---|
| События Telegram за время простоя | ожидают догона | догон по чатам с разрывом через лимитер (ФТ-2.6); при ответе «difference too long» — сверка по истории (ФТ-2.7) |
| SQLite | все подтверждённые записи сохранены (А-6) | Uploader продолжает выгрузку |
| Пачка Uploader | выгружается повторно | upsert даёт тот же результат (ФТ-4.4) |
| Очереди и горячие данные | пустые | пересборка из PostgreSQL от отметок модулей; приём новых событий начинается сразу |
| Исходящее в момент отправки | статус «отправка» в БД | повтор с тем же random_id, Telegram отклоняет дубль (ФТ-9.3) |
| Паузы FloodWait | сохранены в БД | лимитер продолжает паузы (ФТ-10.3) |
| Состояния диалогов | сохранены до отправки ответа | используются как есть (ФТ-8.9) |
| Трассы задач | сохранены в БД | задачи продолжаются с последнего зафиксированного этапа (ФТ-11.6) |
| Пул аккаунтов | состав и состояния в БД | аккаунты подключаются независимо, планировщик распределяет обязанности по мере их готовности (ФТ-1.7) |
| Зависший процесс | — | watchdog перезапускает процесс (НФТ-16) |

## 4. Функциональные требования

### 4.1. Пул аккаунтов

Число аккаунтов меняется от 1 до 10 в любой момент, в том числе внепланово. Обязанности аккаунтов распределяет планировщик по текущему состоянию пула.

- **ФТ-1.1.** Пул содержит от 1 до 10 аккаунтов: пользовательских (MTProto) и ботов. Все функции Системы работают при любом размере пула, включая один аккаунт.
- **ФТ-1.2.** Аккаунт добавляется в пул и выводится из него во время работы, без перезапуска: командой администратора или появлением и удалением файла сессии в каталоге сессий. Вход в новый аккаунт (код подтверждения, пароль) выполняется отдельной утилитой, результат — файл сессии.
- **ФТ-1.3.** У каждого аккаунта есть состояние:
  - active — работает;
  - paused — FloodWait по одному или нескольким методам до указанного времени;
  - restricted — ограничение на отправку (PEER_FLOOD); приём продолжается;
  - disconnected — соединение восстанавливается;
  - lost — сессия отозвана или аккаунт заблокирован (AUTH_KEY_UNREGISTERED, USER_DEACTIVATED_BAN);
  - removed — выведен из пула администратором.

  Каждая смена состояния записывается в журнал. Переход в restricted и lost сопровождается тревогой через другой аккаунт или бота.
- **ФТ-1.4.** Карта членства: для каждого чата Система знает, какие аккаунты пула в нём состоят. Карта строится при подключении аккаунта (один запрос списка диалогов через лимитер) и обновляется по событиям вступления, исключения и удаления чата.
- **ФТ-1.5.** Покрытие чата — число аккаунтов в состоянии active, paused или restricted, состоящих в чате. Требуемое покрытие задаётся в конфиге по роли источника (для касс — 2). Чаты с покрытием ниже требуемого показываются в /coverage и /status; покрытие 0 вызывает тревогу.
- **ФТ-1.6.** Планировщик обязанностей распределяет между аккаунтами:
  - подстраховочный опрос чатов (ФТ-2.5);
  - отправку в группы и внутренние уведомления (ФТ-9.5);
  - активное чтение: догон, сверку, историю (ФТ-10.2).

  Распределение учитывает членство, состояние и остаток бюджета запросов каждого аккаунта и равномерно делит нагрузку.
- **ФТ-1.7.** Планировщик пересчитывает распределение при каждом изменении пула: добавлении, выводе, смене состояния, изменении членства. Новое распределение действует в течение N секунд (конфиг). Задачи выбывшего аккаунта переходят к другим по правилам ФТ-9.4 и ФТ-9.5, все остальные получают статус ожидания с кодом причины (ФТ-11.4).
- **ФТ-1.8.** Каждый аккаунт работает в своём соединении под своим супервизором. Сбой, переподключение или FloodWait аккаунта затрагивает только его самого.
- **ФТ-1.9.** Файлы сессий хранятся вне git, в зашифрованном виде, с доступом только для системного пользователя сервиса. Каждая сессия используется одним процессом.

### 4.2. Приём сообщений

Цель: сообщение, написанное в чат, сразу попадает в БД без FloodWait.

- **ФТ-2.1.** Новые сообщения, правки и удаления поступают через push-обновления, которые Telegram передаёт каждому аккаунту по всем чатам, где он состоит. Все аккаунты пула принимают обновления одновременно.
- **ФТ-2.2.** Каждый аккаунт пишет полученные события независимо. В БД сохраняется первая запись (upsert по chat_id + msg_id, для правок — ещё edit_date), для остальных аккаунтов фиксируется отметка «видел». Push-обновления расходуют только трафик соединения, поэтому повторное покрытие бесплатно для лимитов.
- **ФТ-2.3.** Источнику назначаются роли и политика приёма:
  - full — сохранять и обрабатывать;
  - meta — сохранять факт и время сообщения;
  - presence — фиксировать существование чата;
  - ignore — пропускать.
- **ФТ-2.4.** Политики по умолчанию: роль channel — presence; группы логов Системы — ignore; новый чат без роли — политика из конфига и уведомление в группу logs.
- **ФТ-2.5.** Подстраховочный опрос. Telegram может присылать меньше обновлений для части супергрупп, поэтому каждый аккаунт в состоянии active ведёт короткий опрос getChannelDifference до 10 чатов, с интервалом из поля timeout ответа сервера. Чаты для опроса выбирает планировщик по приоритету источника и признакам пропусков (разрыв pts, тишина дольше нормы). Общий объём опроса растёт и падает вместе с числом аккаунтов: 10 чатов при одном аккаунте, 100 при десяти.
- **ФТ-2.6.** Догон после рестарта или разрыва выполняется по чатам с разрывом, через лимитер аккаунта (ФТ-10.1).
- **ФТ-2.7.** Ответ «difference too long» помечает источник как «разрыв» и запускает сверку открытых сущностей по истории.
- **ФТ-2.8.** История чатов (backfill) загружается отдельным потоком с низким приоритетом и пометкой source=backfill.
- **ФТ-2.9.** Роль отправителя (бот кассы, кассир, сотрудник) определяется по user_id. Пересланное сообщение принадлежит тому, кто его переслал. Сообщения анонимных админов обрабатываются как сообщения чата без прав на команды.
- **ФТ-2.10.** Сообщения аккаунтов пула распознаются как свои по user_id отправителя, в том числе когда приходят как входящие на другой аккаунт пула. Они получают origin=system (отправлены через Вывод) или origin=human (написаны вручную). Правила реакции срабатывают на сообщения внешних отправителей.
- **ФТ-2.11.** Кассы — супергруппы (id вида -100…): в них номер сообщения общий для всех аккаунтов, и дедупликация точная. Обычные группы дедуплицируются по отправителю, времени и хешу текста и отмечаются в /coverage как источники с приблизительной дедупликацией.

### 4.3. Извлечение (Extractor)

- **ФТ-3.1.** Extractor сохраняет метаданные:
  - аккаунт-источник, chat_id, msg_id, отправитель;
  - время сообщения, время правки, время приёма в Систему;
  - reply_to, origin;
  - тип медиа и ссылку на файл;
  - номер версии, хеш текста, версию манифеста, trace_id задачи.
- **ФТ-3.2.** Extractor сохраняет нормализованный текст целиком. Из обёртки события Telegram сохраняются поля ФТ-3.1.
- **ФТ-3.3.** Перед извлечением текст очищается от разметки Telegram: `[1481598133](tel:1481598133)` → `1481598133`.
- **ФТ-3.4.** Extractor извлекает признаки по манифесту:
  - числа по длине;
  - суммы в разных форматах («5 001.34», «3500.00», «4 001,36»);
  - телефоны, номера карт, @username, ссылки;
  - заголовок в квадратных скобках;
  - пары «Метка: значение»;
  - слова из словарей после нормализации (регистр, ё→е, транслит, начальная форма);
  - маркеры (✅, ❌, 🔴 и др.);
  - команды.
- **ФТ-3.5.** Шаблон делит значение метки на подполя:
  - `Пользователь: @x ID: 7287295969` → имя + TGID;
  - `Успешных депозитов: 🔴 52 (всего: 52)` → маркер + два числа;
  - `Метод оплаты: … 3 000 - 500 000` → название метода + лимиты.
- **ФТ-3.6.** Каждый признак сохраняется с позицией и ближайшей меткой. Смысл признака (TGID, MelID, Deposit ID) назначает сортировщик.
- **ФТ-3.7.** Манифест описывает формы признаков. Условия и логика задаются в правилах сортировщика и реакций.
- **ФТ-3.8.** Регулярные выражения манифеста проверяются при загрузке и выполняются по условию А-7. Применяется манифест, прошедший проверку.
- **ФТ-3.9.** При смене версии манифеста признаки пересчитываются для сообщений, текст которых ещё хранится.

### 4.4. Резервный буфер (SQLite) и Uploader

- **ФТ-4.1.** Запись Extractor сначала фиксируется в SQLite (А-6). С этого момента событие считается принятым.
- **ФТ-4.2.** Uploader выгружает записи в PostgreSQL пачками (А-1) в порядке поступления.
- **ФТ-4.3.** Запись в SQLite помечается выгруженной после подтверждения фиксации в PostgreSQL и хранится резервный срок из конфига.
- **ФТ-4.4.** Повторная выгрузка выполняется как upsert по (аккаунт, chat_id, msg_id, версия) и даёт тот же результат.
- **ФТ-4.5.** При старте Система сверяет фактические значения journal_mode и synchronous с требуемыми и запускается при их совпадении; при расхождении — тревога и остановка.
- **ФТ-4.6.** Объём невыгруженного остатка ограничен местом на диске. При приближении к лимиту уходит тревога; при достижении приём продолжается для источников высшего приоритета.

### 4.5. Хранение (PostgreSQL)

- **ФТ-5.1.** Сообщения хранятся в таблице, разбитой по месяцам: метаданные, текст, признаки, а после сортировки — тип и поля (JSONB).
- **ФТ-5.2.** Новая версия сообщения сохраняется при изменении текста.
- **ФТ-5.3.** Срок хранения текста задаётся по типу сообщения. По истечении срока текст удаляется или архивируется (zstd со словарём). Извлечённые поля хранятся бессрочно.
- **ФТ-5.4.** Устаревшие данные удаляются отключением месячных разделов.
- **ФТ-5.5.** Ядро хранит:
  - пул аккаунтов, журнал их состояний и паузы FloodWait;
  - карту членства и текущее распределение обязанностей;
  - источники и их роли;
  - пользователей Telegram с историей имён и роли сотрудников;
  - сообщения и их версии;
  - общее хранилище сущностей (тип, ключ, состояние, атрибуты JSONB) и связи между ними;
  - состояния диалогов;
  - исходящие задачи и попытки отправки;
  - трассы задач (п. 4.11);
  - журнал срабатываний правил и отметки обработки модулей.
- **ФТ-5.6.** Модуль хранит данные в общем хранилище сущностей или в собственных таблицах для скорости отчётов. Общее хранилище подключает новую сущность без миграций.

### 4.6. Сортировщик

- **ФТ-6.1.** Сортировщик присваивает каждому сообщению тип по правилам из конфигурации. Условия правила строятся над ролью источника, ролью отправителя, заголовком, словами, метками и другими признаками.
- **ФТ-6.2.** Правило задаёт:
  - сопоставление меток именованным полям («Номер счёта» → mel_id);
  - ключ упорядочения (чат, Deposit ID и т. п.);
  - класс приоритета;
  - срок хранения текста.
- **ФТ-6.3.** Правила группируются в шаблоны. Источник ссылается на шаблон и переопределяет его часть; один шаблон обслуживает все типовые кассы.
- **ФТ-6.4.** Сообщение без подходящего правила получает тип unknown, финальный статус «пропущено» с кодом UNKNOWN_TYPE и учитывается в счётчике по источнику. Сводка по unknown периодически отправляется в группу debug.
- **ФТ-6.5.** Результат сортировки записывается через пакетный писатель (А-4).

### 4.7. Менеджер очереди сортировщика

- **ФТ-7.1.** Модуль подписывается на типы сообщений, в том числе по маске (deposit.*, *). Менеджер доставляет сообщение всем подписчикам.
- **ФТ-7.2.** У каждого модуля своя очередь с ограниченной длиной и свой лимит параллельности.
- **ФТ-7.3.** В каждой очереди три полосы приоритета:
  1. команды;
  2. живой поток;
  3. backfill — обрабатывается, пока живая полоса ниже порога, с ограничением скорости.
- **ФТ-7.4.** Внутри полосы действует приоритет из конфигурации: по источнику, партнёру и др.
- **ФТ-7.5.** События с одним ключом упорядочения обрабатываются строго последовательно, с разными — параллельно. Порядок по ключу старше приоритета полос: если по ключу есть необработанные события backfill, живые события этого ключа ждут, а backfill этого ключа поднимается в приоритете.
- **ФТ-7.6.** При превышении порога длины очереди или задержки модуля в группу logs отправляется предупреждение.
- **ФТ-7.7.** У каждого модуля есть отметка последнего обработанного события. После рестарта обработка продолжается с неё.

### 4.8. Модули, действия и правила

- **ФТ-8.1.** Модуль объявляет:
  - подписки на типы сообщений;
  - сущности, которые ведёт, и место их хранения;
  - команды, которые обслуживает;
  - свой раздел конфигурации;
  - лимит параллельности и таймаут обработки события.
- **ФТ-8.2.** Обработка идемпотентна: повторная обработка события даёт тот же результат.
- **ФТ-8.3.** Внешние действия (send, reply, notify, ask) создают исходящие задачи в Выводе в одной транзакции с отметкой модуля. Уникальный ключ задачи — «событие + правило»: повтор после сбоя находит уже созданную задачу.
- **ФТ-8.4.** Ядро предоставляет фундаментальные действия:

| Действие | Назначение |
|---|---|
| match | поиск совпадений: точный, нечёткий, в окне времени; возвращает кандидатов с оценкой |
| lookup / upsert | поиск, создание и обновление сущности |
| link | связь сообщения с сущностью или сущностей между собой |
| set_state | изменение состояния сущности или диалога, в том числе с таймаутом |
| render | текст по шаблону (Jinja2 в режиме sandbox) |
| send / reply | исходящая задача в Вывод |
| notify | сообщение в группу или сотруднику с заданной ролью |
| ask | уточняющий вопрос с ожиданием ответа через состояние диалога |
| schedule | событие по таймеру |
| report | список или сводка по именованному запросу |

- **ФТ-8.5.** Правило реакции состоит из частей:
  - когда — тип события, команда или таймер;
  - если — условие над полями, состоянием и сущностями (CEL или JSONLogic);
  - то — цепочка действий, где результат предыдущего доступен следующему и есть ветвление по результату;
  - приоритет, признак вкл/выкл, версия.
- **ФТ-8.6.** Правило запускается в режиме dry-run: оно записывает в журнал планируемые действия и создаёт задачи со статусом «симуляция». Правило прогоняется по сохранённой истории.
- **ФТ-8.7.** Каждое срабатывание правила записывается в журнал: правило и версия, trace_id события, входные данные, выполненные действия и созданные задачи.
- **ФТ-8.8.** Для событий source=backfill выполняются внутренние действия: match, lookup, upsert, link, set_state, report.
- **ФТ-8.9.** Состояние диалога записывается в БД до отправки ответа.
- **ФТ-8.10.** Автоответ в диалог отправляется, если за последние N минут в нём нет сообщений origin=human (N в конфиге).
- **ФТ-8.11.** Обработка события ограничена таймаутом модуля. При ошибке или таймауте задача получает статус с кодом MODULE_ERROR или MODULE_TIMEOUT, очередь модуля продолжает работу. Задачу можно перезапустить командой (ФТ-11.9).

### 4.9. Вывод и отправка

- **ФТ-9.1.** Все исходящие сообщения проходят через Вывод как исходящие задачи с трассой (п. 4.11).
- **ФТ-9.2.** Каждый аккаунт отправляет свои задачи последовательно; разные аккаунты отправляют параллельно.
- **ФТ-9.3.** random_id генерируется и сохраняется в задаче до отправки. Повтор идёт с тем же random_id; ответ RANDOM_ID_DUPLICATE означает, что сообщение уже доставлено, и задача получает статус «доставлено».
- **ФТ-9.4.** Ответ в личном диалоге отправляет аккаунт этого диалога. Пока он вне состояния active, задача ждёт его до конца срока жизни со статусом «ожидает» и кодом причины (ACCOUNT_PAUSED, ACCOUNT_RESTRICTED, ACCOUNT_LOST). Так игрок всегда получает ответ от того аккаунта, которому писал.
- **ФТ-9.5.** Сообщение в группу и внутреннее уведомление отправляет любой аккаунт пула в состоянии active, состоящий в чате и имеющий остаток бюджета. При выбытии назначенного аккаунта задача переходит к другому подходящему; при отсутствии подходящих — ждёт с кодом NO_ACCOUNT_IN_CHAT.
- **ФТ-9.6.** У каждой исходящей задачи есть срок жизни по типу. По истечении срока задача получает финальный статус «истёк срок» (TTL_EXPIRED) с последней причиной ожидания.
- **ФТ-9.7.** Темп отправки задаётся в конфиге по аккаунту и по чату. Для ботов — в пределах опубликованных ориентиров Telegram: около 1 сообщения в секунду в один чат, до 20 в минуту в группу, около 30 в секунду всего. Для пользовательских аккаунтов — более консервативные значения.
- **ФТ-9.8.** Порядок отправки: ответы на команды, ответы клиентам, уведомления, массовые сообщения.

### 4.10. Бюджет запросов к Telegram

Push-обновления приходят без расхода лимитов. Лимиты расходуют активные вызовы: подстраховочный опрос, догон, сверка, история, запрос сущностей, отправка и редактирование. Для пользовательских аккаунтов Telegram их не публикует, поэтому Система управляет ими явно.

- **ФТ-10.1.** Все вызовы API одного аккаунта идут через лимитер этого аккаунта: одновременно 1–2 запроса (значение в конфиге). Разные аккаунты работают параллельно, и общий бюджет Системы растёт с числом аккаунтов.
- **ФТ-10.2.** Бюджет аккаунта делится по приоритету:
  1. ответы на команды;
  2. ответы клиентам;
  3. подстраховочный опрос, догон и сверка;
  4. уведомления;
  5. backfill — из остатка.
- **ФТ-10.3.** Автоматическое ожидание FloodWait внутри библиотеки выключено (flood_sleep_threshold=0). FloodWait обрабатывает лимитер: ставит паузу на метод или аккаунт, снижает темп, сохраняет срок паузы в БД и переводит аккаунт в paused. Планировщик передаёт его обязанности другим аккаунтам на время паузы.
- **ФТ-10.4.** Сущности (пользователи, чаты, access_hash) кешируются из приходящих обновлений, и обработка сообщений использует этот кеш (А-8).
- **ФТ-10.5.** Ошибки Telegram обновляют состояние пула и карту членства:

| Ошибка Telegram | Результат |
|---|---|
| FLOOD_WAIT_X | аккаунт или метод → paused до истечения X |
| PEER_FLOOD | аккаунт → restricted |
| USER_DEACTIVATED_BAN, AUTH_KEY_UNREGISTERED | аккаунт → lost |
| CHANNEL_PRIVATE, USER_KICKED, удаление чата | связка «аккаунт — чат» удаляется из карты членства |
| CHAT_WRITE_FORBIDDEN, USER_BANNED_IN_CHANNEL | аккаунт остаётся читателем чата и выбывает из отправителей в него |
| USER_IS_BLOCKED | клиент заблокировал аккаунт; диалог помечается для сотрудников |

Каждая такая ошибка сразу переводит зависящие задачи в статус ожидания или финальный статус с кодом причины (ФТ-11.8).

### 4.11. Трассировка задач и контроль доставки

Каждая задача имеет в БД трассу: этапы, отметки времени, текущий статус и код причины. По трассе видно, где задача сейчас, сколько она провела на каждом этапе и чем закончилась.

Исходящая задача ждёт аккаунт или конец паузы с видимой причиной и заканчивается одним из трёх финалов.

- **ФТ-11.1.** Задачи бывают двух видов: входящая (событие Telegram) и исходящая (сообщение Вывода). Каждая получает trace_id при создании. Исходящая хранит trace_id породившей её входящей задачи, правило и его версию.
- **ФТ-11.2.** Этапы входящей задачи: принято (с отметкой аккаунта) → извлечено → в буфере → в PostgreSQL → отсортировано (тип) → в очереди модуля → обработано модулем. Два последних этапа фиксируются отдельно для каждого модуля-подписчика.
- **ФТ-11.3.** Этапы исходящей задачи: создана → в очереди Вывода → назначен аккаунт → отправка → доставлено (msg_id). Каждая попытка отправки сохраняется отдельно: аккаунт, время, результат, код ошибки Telegram.
- **ФТ-11.4.** Статусы задачи:
  - в работе — задача на одном из этапов;
  - ожидает — с кодом причины и временем, до которого ждёт;
  - финальные: доставлено, обработано, пропущено, не доставлено, истёк срок, отменено, симуляция. Все финальные статусы, кроме «доставлено» и «обработано», сопровождаются кодом причины.
- **ФТ-11.5.** Коды причин ведутся справочником:

| Код | Значение | Статус |
|---|---|---|
| FLOOD_WAIT | аккаунт или метод на паузе до времени T | ожидает |
| ACCOUNT_PAUSED | нужный аккаунт в состоянии paused или disconnected | ожидает |
| NO_ACCOUNT_IN_CHAT | в чате нет активного аккаунта пула | ожидает |
| DB_UNAVAILABLE | PostgreSQL недоступен | ожидает |
| ACCOUNT_RESTRICTED | аккаунт ограничен на отправку (PEER_FLOOD) | ожидает / не доставлено |
| ACCOUNT_LOST | аккаунт заблокирован или сессия отозвана | ожидает / не доставлено |
| CHAT_DELETED | чат удалён или аккаунт исключён (CHANNEL_PRIVATE, USER_KICKED) | не доставлено |
| CHAT_WRITE_FORBIDDEN | у аккаунта нет права писать в чат | не доставлено |
| USER_IS_BLOCKED | клиент заблокировал аккаунт | не доставлено |
| TTL_EXPIRED | истёк срок жизни задачи | истёк срок |
| MODULE_ERROR, MODULE_TIMEOUT | ошибка или таймаут модуля | ожидает перезапуска |
| UNKNOWN_TYPE | сообщение без подходящего правила | пропущено |

  Новый код ошибки Telegram сохраняется как есть и попадает в сводку для пополнения справочника.
- **ФТ-11.6.** Каждая смена этапа и статуса фиксируется в БД. Переходы в «ожидает», «отправка» и финальные статусы записываются синхронно, промежуточные этапы — пакетным писателем. После рестарта незавершённые задачи продолжаются с последнего зафиксированного этапа.
- **ФТ-11.7.** Для каждого этапа задан норматив времени (конфиг). Задача, превысившая норматив, получает отметку «зависла» и попадает в /stuck. При массовом зависании на одном этапе (порог в конфиге) уходит тревога с названием этапа.
- **ФТ-11.8.** При выбытии аккаунта, удалении чата или исключении аккаунта из чата все зависящие задачи сразу переходят к другому аккаунту (ФТ-9.5) или получают статус «ожидает» или «не доставлено» с кодом причины.
- **ФТ-11.9.** Команды отладки:

| Команда | Результат |
|---|---|
| `/trace <trace_id \| Deposit ID \| ссылка на сообщение>` | все этапы задачи и связанных задач с длительностью каждого, попытки отправки, коды причин |
| `/stuck [этап]` | зависшие задачи, сгруппированные по этапу и коду причины |
| `/retry <trace_id \| фильтр>` | перезапуск задач с текущего этапа |
| `/cancel <trace_id \| фильтр>` | отмена задач с записью автора |
| `/queue` | длины очередей модулей и Вывода по аккаунтам |
| `/accounts` | пул: состояние, паузы FloodWait, остаток бюджета, текущие обязанности |
| `/coverage` | чаты с покрытием ниже требуемого и с приблизительной дедупликацией |
| `/status` | сводка по всему вышеперечисленному |

- **ФТ-11.10.** Метрики по этапам: медиана и 95-й перцентиль длительности, число задач на каждом этапе, распределение финальных статусов по кодам причин. Метрики строятся по источнику, модулю и аккаунту.
- **ФТ-11.11.** Хранение трасс:
  - одна строка на входящую задачу с отметками времени этапов;
  - строка на каждую обработку модулем;
  - строка на исходящую задачу и строка на каждую попытку отправки.

  Детальные трассы хранятся N дней (конфиг), агрегированные метрики — бессрочно.

### 4.12. Команды, роли и права

- **ФТ-12.1.** Роли пользователей: player, casher, manager, admin, support, dev. У пользователя может быть несколько ролей. Роль бывает глобальной или привязанной к источнику (кассир конкретной кассы).
- **ФТ-12.2.** Перечень ролей источников и ролей пользователей расширяется конфигурацией.
- **ФТ-12.3.** Команда — правило с триггером-командой. Поддерживаются форматы `/имя аргументы` и команда без слэша (`scam 1481598133`, `unban 1481598133`). Аргументы проверяются по типу.
- **ФТ-12.4.** Права задаются матрицей «роль пользователя × роль источника → допустимые команды». Команда пользователя с недостаточными правами получает отказ и финальный статус «отменено» с кодом ACCESS_DENIED.
- **ФТ-12.5.** Аргумент-идентификатор может быть TGID или MelID. Префикс (mel:, tg:) задаёт тип явно; без префикса Система ищет по обоим типам и при двух разных игроках запрашивает уточнение.
- **ФТ-12.6.** Команды чтения (/summ, /status, /trace и др.) отвечают из агрегатов в памяти и индексированных таблиц. Для тяжёлого отчёта Система сразу подтверждает приём команды и присылает результат по готовности.
- **ФТ-12.7.** Каждая команда — задача с трассой: автор, источник, аргументы, результат.

### 4.13. Конфигурация

- **ФТ-13.1.** Конфигурация хранится в YAML-файлах под git:
  - пул аккаунтов, требуемое покрытие, темп и лимиты запросов;
  - источники, роли и политики приёма;
  - манифест признаков и словари;
  - шаблоны и правила сортировки;
  - правила реакции и шаблоны текстов;
  - матрица прав;
  - приоритеты, сроки жизни исходящих, сроки хранения;
  - нормативы времени этапов и пороги тревог.
- **ФТ-13.2.** Конфигурация проверяется по схеме при загрузке. До успешной проверки действует прежняя версия, ошибка отправляется в группу logs.
- **ФТ-13.3.** Конфигурация перезагружается командой без рестарта Системы.
- **ФТ-13.4.** Каждая запись журнала и трасса ссылаются на версию конфигурации, действовавшую в момент события.
- **ФТ-13.5.** Веб-админка (этап 5) редактирует те же структуры, что и файлы.

## 5. Требования к первым модулям

Первые модули — «Заявки» и «Игроки»; на них принимается конструктор. Тикеты, промокоды, посты и отчёты описываются отдельными ТЗ.

### 5.1. Модуль «Заявки»

- **ФТ-З.1.** Касса — источник с ролью kassa, определяется по chat_id. Кассиры кассы — один или несколько людей с ролью casher в этой кассе.
- **ФТ-З.2.** Метод оплаты идентифицируется по названию без лимитов и по method_id из команд `/change_dep_limits N`, `/turn_on N`, `/turn_off N` и ответов бота. История лимитов и включений метода хранится.
- **ФТ-З.3.** Ключ заявки — Deposit ID, общий для всех касс.
- **ФТ-З.4.** Модуль ведёт стадии заявки и время каждой:

| Стадия | Сообщение-источник | Связь с заявкой |
|---|---|---|
| создана | «[ДЕПОЗИТ ТРЕУГОЛЬНИК]», «[ДЕПОЗИТ ПРЕДУСТАНОВЛЕННАЯ СУММА]» и др. | Deposit ID |
| реквизиты выданы кассиром | сообщение кассира с реквизитами | reply_to или следующее подтверждение бота с TGID |
| реквизиты отправлены игроку | «Реквизиты успешно отправлены пользователю ID …» (бонус, итоговая сумма) | TGID + чат + открытая заявка |
| чек получен | «[ДЕПОЗИТ]» | Deposit ID; сумма = запрошенная + бонус |
| финал ✅ / ❌ | правка сообщения «[ДЕПОЗИТ]» | Deposit ID |
| отменена | правка сообщения «создана» (инициатор, причина) | Deposit ID |
| перенаправлена | ответ бота на /turn_off | метод + открытые заявки |

- **ФТ-З.5.** После финала (✅, ❌ или отмена) статус заявки фиксируется и заявка закрывается. До финала отслеживаются все правки её сообщений; заявка остаётся открытой от секунд до нескольких дней.
- **ФТ-З.6.** При перенаправлении заявка сохраняет историю касс.
- **ФТ-З.7.** Заявка без Deposit ID (например, у TRUSTED-пользователей) связывается по TGID, сумме и времени. OCR-предупреждения прикрепляются к заявке как отметки.
- **ФТ-З.8.** Модуль считает по кассе, кассиру и периоду:
  - число заявок и среднюю сумму;
  - время выдачи реквизитов и время до финала;
  - долю успешных, отклонённых и отменённых;
  - время работы и простоя методов.
- **ФТ-З.9.** До начала разработки на живом API проверяется, отвечают ли кассиры reply на заявку. Реквизиты привязываются по reply или по подтверждению бота с TGID: кассир может отправить два набора реквизитов подряд.
- **ФТ-З.10.** Сверка: заявки без финала старше X минут периодически перечитываются из Telegram пачкой id по чату, в рамках бюджета ФТ-10.2.
- **ФТ-З.11.** Заявка без финала дольше Y часов получает статус «зависла», попадает в сводку для сотрудников и учитывается в статистике отдельно.

### 5.2. Модуль «Игроки»

- **ФТ-И.1.** Идентификаторы игрока — TGID и MelID. Каждая заявка добавляет связь TGID ↔ MelID. Игрок — связная группа идентификаторов: если на один MelID создавали заявки разные TGID, это один игрок.
- **ФТ-И.2.** Слияние игроков выполняется по TGID и MelID. Имя и username хранятся как история.
- **ФТ-И.3.** Каждое слияние записывается в журнал; доступно ручное разделение. Слияние групп размером выше порога подтверждает сотрудник.
- **ФТ-И.4.** Запросы:
  - депозиты игрока по всем кассам за период;
  - список TGID и MelID игрока.
- **ФТ-И.5.** У игрока хранятся санкции и отметки: страйки (scam), блокировка и разблокировка (unban), жалобы, обращения, заметки операторов. Каждая запись хранит автора и время.
