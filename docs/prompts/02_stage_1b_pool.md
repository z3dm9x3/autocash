# Этап 1b. Пул аккаунтов, лимитер и маршрутизация отправки

> Контекст — `CLAUDE.md`. Предыдущий шаг (1a) дал сквозной конвейер на одном аккаунте. Теперь превращаем его в динамический пул из 1–10 аккаунтов. Конвейер 1a переписывать не нужно, только подключить к нему пул.

## Цель

Система работает при любом числе аккаунтов от 1 до 10. Аккаунты добавляются, выбывают, ловят FloodWait и баны прямо во время работы, а обязанности перераспределяются за N секунд без перезапуска. Активные вызовы API никогда не приводят к FloodWait из-за нашей собственной неаккуратности.

## Что сделать

### 1. Пул и состояния (ФТ-1.1–1.3, 1.8, 1.9)
- 1–10 аккаунтов: пользовательские (MTProto) и боты. Каждый работает в своём соединении под своим супервизором; сбой одного затрагивает только его.
- Добавление и вывод без рестарта: командой администратора или появлением/удалением файла сессии в каталоге сессий. Вход в аккаунт (код, пароль) делает **отдельная CLI-утилита**, её результат — файл сессии.
- Состояния: `active`, `paused` (FloodWait по методу или аккаунту до времени T), `restricted` (PEER_FLOOD; приём продолжается), `disconnected`, `lost` (AUTH_KEY_UNREGISTERED, USER_DEACTIVATED_BAN), `removed`. Каждая смена пишется в журнал. Переход в `restricted` и `lost` сопровождается тревогой **через другой аккаунт или бота**.
- Сессии хранятся вне git, зашифрованными, с правами только для системного пользователя, одна сессия — один процесс.

### 2. Членство и покрытие (ФТ-1.4, 1.5)
- Карта «чат → аккаунты»: строится при подключении аккаунта одним запросом списка диалогов через лимитер, обновляется по событиям вступления, исключения и удаления чата.
- Покрытие = число аккаунтов в active/paused/restricted в чате. Требуемое покрытие задаётся по роли источника (для касс 2). Недопокрытые чаты попадают в `/coverage` и `/status`; покрытие 0 → тревога.

### 3. Мультиаккаунтный приём (ФТ-2.1, 2.2)
- Все аккаунты принимают push-обновления одновременно. В БД сохраняется первая запись (upsert по `chat_id + msg_id`, для правок ещё и `edit_date`), для остальных аккаунтов ставится отметка «видел».

### 4. Планировщик обязанностей (ФТ-1.6, 1.7)
- Распределяет: подстраховочный опрос, отправку в группы и внутренние уведомления, активное чтение (догон, сверка, история).
- Учитывает членство, состояние и остаток бюджета каждого аккаунта, делит нагрузку равномерно.
- Пересчёт при любом изменении: добавление, вывод, смена состояния, изменение членства. Новое распределение вступает в силу за N секунд (конфиг, OPEN-QUESTION). Задачи выбывшего аккаунта переходят к другим по ФТ-9.4/9.5, остальные получают «ожидает» с кодом причины.

### 5. Подстраховочный опрос, догон, разрывы (ФТ-2.5–2.7)
- Каждый `active` аккаунт ведёт короткий опрос `getChannelDifference` до 10 чатов с интервалом из поля `timeout` ответа сервера. Чаты выбирает планировщик по приоритету источника и признакам пропусков (разрыв pts, тишина дольше нормы). Объём масштабируется с пулом: 10 чатов при одном аккаунте, 100 при десяти.
- Догон после рестарта или разрыва идёт только по чатам с разрывом, через лимитер.
- «difference too long» → источник помечается как «разрыв», запускается сверка. В ядре сделай хук «сверка открытых сущностей по истории», который модули реализуют на этапе 2.

### 6. Лимитер и бюджет (ФТ-10.1–10.5)
- Все вызовы API одного аккаунта идут через его лимитер: одновременно 1–2 запроса (конфиг). Разные аккаунты работают параллельно.
- Приоритеты бюджета: (1) ответы на команды, (2) ответы клиентам, (3) опрос, догон, сверка, (4) уведомления, (5) backfill из остатка.
- `flood_sleep_threshold=0`. При FloodWait лимитер ставит паузу на метод или аккаунт, снижает темп, сохраняет срок паузы в БД (переживает рестарт) и переводит аккаунт в `paused`; планировщик на это время передаёт обязанности другим.
- Сущности (users, chats, access_hash) кешируются из приходящих updates (А-8).
- Ошибки Telegram сразу меняют пул и членство:

| Ошибка | Результат |
|---|---|
| FLOOD_WAIT_X | аккаунт/метод → paused до X |
| PEER_FLOOD | аккаунт → restricted |
| USER_DEACTIVATED_BAN, AUTH_KEY_UNREGISTERED | аккаунт → lost |
| CHANNEL_PRIVATE, USER_KICKED, удаление чата | связка «аккаунт — чат» удаляется из карты |
| CHAT_WRITE_FORBIDDEN, USER_BANNED_IN_CHANNEL | аккаунт остаётся читателем, выбывает из отправителей в этот чат |
| USER_IS_BLOCKED | диалог помечается для сотрудников |

  Зависящие задачи сразу получают «ожидает» или финальный статус с кодом причины (ФТ-11.8).

### 7. Маршрутизация Вывода (ФТ-9.2, 9.4–9.8)
- Каждый аккаунт отправляет свои задачи последовательно, разные аккаунты — параллельно.
- **Личный диалог** отвечает только аккаунт этого диалога. Пока он не `active`, задача ждёт до конца TTL с `ACCOUNT_PAUSED` / `ACCOUNT_RESTRICTED` / `ACCOUNT_LOST`.
- **Группа и внутреннее уведомление** — любой `active` аккаунт, состоящий в чате и с остатком бюджета. При выбытии назначенного задача переходит к другому; если подходящих нет — ждёт с `NO_ACCOUNT_IN_CHAT`.
- TTL по типу исходящего (конфиг, OPEN-QUESTION). По истечении — финал «истёк срок» (`TTL_EXPIRED`) с последней причиной ожидания.
- Темп по аккаунту и чату из конфига. Боты: около 1 сообщения/с в чат, до 20/мин в группу, около 30/с всего. Пользовательские аккаунты — консервативнее (дефолты задокументируй).
- Порядок отправки: ответы на команды → ответы клиентам → уведомления → массовые.

## Вне рамок 1b
Команды отладки и метрики (1c), сверка по существу (этап 2), backfill (этап 4).

## Критерии приёмки 1b (каждый — тест на фейковом Telegram)
1. Пул меняется 3 → 1 и 1 → 10 во время работы: распределение обязанностей и покрытие обновляются за N секунд, сообщения не теряются.
2. Догон 100 чатов проходит без единого FloodWait (фейковый сервер выдаёт FloodWait при превышении темпа).
3. FloodWait у аккаунта → `paused`, пауза сохранена в БД и переживает рестарт, обязанности переходят к другим, по окончании паузы аккаунт возвращается.
4. PEER_FLOOD → `restricted` + тревога через другой аккаунт; приём на нём продолжается.
5. Бан → `lost`, тревога; групповые задачи ушли другим аккаунтам, личные ждут с `ACCOUNT_LOST` и по TTL получают `TTL_EXPIRED`.
6. Удаление чата или исключение аккаунта → членство обновлено, задачи переназначены или ждут с `NO_ACCOUNT_IN_CHAT`.
7. Одно сообщение, принятое тремя аккаунтами, записано один раз с тремя отметками «видел».
8. Своё сообщение, пришедшее на другой аккаунт пула, получает верный `origin` и не запускает правила.
9. Пул из одного аккаунта: все функции работают.
