# Этап 3. Движок правил реакции, диалоги, команды-правила

> Контекст — `CLAUDE.md`. Ядро, «Заявки» и «Игроки» готовы. Теперь система начинает **сама писать в Telegram** с пользовательских аккаунтов. Главные риски этапа — дубли, ответы поверх живого сотрудника и спам-ограничения (НФТ-12). Каждое внешнее действие должно быть безопасным по умолчанию.

## Что сделать

### 1. Правило реакции (ФТ-8.5, 13.1)
- Структура: **когда** (тип события, команда или таймер) → **если** (условие над полями, состоянием и сущностями) → **то** (цепочка действий, результат предыдущего доступен следующему, ветвление по результату). Плюс приоритет, вкл/выкл, версия.
- Язык условий: CEL или JSONLogic. Выбери один, обоснуй в `docs/decisions.md` (безопасность, скорость, читаемость для автора конфига). Условия выполняются без доступа к произвольному Python.
- Правила лежат в YAML, проверяются схемой и перезагружаются без рестарта.

### 2. Внешние и служебные действия (ФТ-8.4)
- `render` — текст по шаблону, Jinja2 в sandbox.
- `send` / `reply` — исходящая задача в Вывод.
- `notify` — сообщение в группу или сотруднику с заданной ролью.
- `ask` — уточняющий вопрос и ожидание ответа через состояние диалога с таймаутом.
- `schedule` — событие по таймеру; переживает рестарт.
- Внешние действия создают исходящие задачи в одной транзакции с отметкой модуля; уникальный ключ «событие + правило» (ФТ-8.3).

### 3. Диалоги и автоответы (ФТ-8.9, 8.10)
- Личные сообщения игроков обрабатываются полностью. Ответ в личке отправляет только аккаунт этого диалога (ФТ-9.4).
- Состояние диалога пишется в БД **до** отправки ответа.
- Автоответ отправляется, только если за последние N минут в диалоге нет сообщений `origin=human` (N в конфиге, OPEN-QUESTION). Ручной ответ сотрудника с того же аккаунта гасит автоматику.
- `USER_IS_BLOCKED` помечает диалог для сотрудников.

### 4. Dry-run и журнал (ФТ-8.6, 8.7)
- Режим dry-run: правило пишет в журнал планируемые действия и создаёт задачи со статусом «симуляция», ничего не отправляя.
- Прогон правила по сохранённой истории за период: отчёт «что бы сработало и что бы отправилось».
- Журнал каждого срабатывания: правило и версия, trace_id события, входные данные, выполненные действия, созданные задачи.

### 5. Команды как правила (ФТ-12.3–12.5)
- Команда — правило с триггером-командой. Форматы: `/имя аргументы` и без слэша (`scam 1481598133`, `unban 1481598133`). Аргументы проверяются по типу.
- Идентификатор: TGID или MelID; префиксы `mel:` / `tg:`; без префикса — поиск по обоим и уточнение через `ask` при двух разных игроках.
- Права — по матрице этапа 1c; отказ → `ACCESS_DENIED`.
- Реализуй `scam` (страйк) и `unban` поверх санкций модуля «Игроки», с автором и временем.

### 6. Защита от спам-ограничений (НФТ-12)
- Для пользовательских аккаунтов — консервативный темп из конфига, лимит автоответов на диалог и на аккаунт в единицу времени, отключение автоматики аккаунта при `restricted`.
- Массовые рассылки — самый низкий приоритет (ФТ-9.8).

## Критерии приёмки этапа 3
1. Правило включается, выключается и меняется через конфиг без рестарта; невалидное правило не применяется, ошибка уходит в `logs`.
2. Dry-run создаёт только задачи «симуляция» и записи журнала; прогон по истории даёт отчёт.
3. Автоответ не отправляется, если сотрудник писал в диалог за последние N минут (тест с `origin=human`).
4. Каждая исходящая задача доходит до финального статуса: доставлено, или не доставлено / истёк срок с кодом причины.
5. `kill -9` между записью состояния диалога и отправкой: после рестарта ответ уходит ровно один раз.
6. `scam` / `unban` без прав → `ACCESS_DENIED`; с правами → запись в санкциях игрока с автором.
7. Неоднозначный идентификатор без префикса → уточняющий вопрос, после ответа команда выполняется.
