# Этап 4. Загрузка истории чатов (backfill)

> Контекст — `CLAUDE.md`. Полосы приоритета и порядок по ключу уже есть с этапа 1a, здесь их нагружаем по-настоящему.

## Цель

Загрузить историю касс и других источников за период из конфига (OPEN-QUESTION), восстановить по ней заявки, игроков и статистику и при этом не замедлить живой поток.

## Что сделать

1. **Отдельный поток загрузки** (ФТ-2.8): события помечаются `source=backfill`. Загрузка идёт через лимитеры аккаунтов из остатка бюджета (приоритет 5, ФТ-10.2). Планировщик распределяет чаты между аккаунтами по членству.
2. **Нижняя полоса очереди** (ФТ-7.3): backfill обрабатывается, пока живая полоса ниже порога, с ограничением скорости.
3. **Порядок по ключу** (ФТ-7.5): если по ключу (например, Deposit ID) есть необработанный backfill, живые события этого ключа ждут, а backfill ключа поднимается в приоритете. Это главное место для гонок: покрой его тестами.
4. **Только внутренние действия** (ФТ-8.8): для `source=backfill` выполняются `match`, `lookup`, `upsert`, `link`, `set_state`, `report`. Внешние действия (`send`, `reply`, `notify`, `ask`, `schedule`) **не выполняются** и не создают исходящих задач; факт пропуска пишется в журнал правил.
5. **Возобновляемость**: прогресс загрузки по каждому чату хранится в БД и продолжается после рестарта и после FloodWait без повторной загрузки.
6. **Управление**: команды запуска, паузы и статуса загрузки; прогресс виден в `/status`.

## Критерии приёмки этапа 4
1. Во время загрузки истории выполняются НФТ-5 (команда чтения ≤ 1 с) и НФТ-6 (живой поток ≤ 1 с). Нагрузочный тест: живой поток ×10 плюс backfill.
2. Для событий истории не создана ни одна исходящая задача.
3. Живое событие по ключу, у которого в очереди есть backfill, обрабатывается после него; итоговое состояние заявки совпадает с эталоном.
4. Рестарт посреди загрузки: продолжение с места остановки, без дублей в сущностях.
5. Загрузка не вызывает FloodWait на аккаунтах, обслуживающих живые ответы.
