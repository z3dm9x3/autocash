# Этап 5. Веб-админка

> Контекст — `CLAUDE.md`. Монолит (П-7): админка — часть того же приложения или отдельный процесс на том же сервере, работающий с теми же структурами. Стек фронтенда в ТЗ не задан: предложи вариант, который укладывается в 2 ядра / 8 ГБ рядом с основным сервисом, и дождись подтверждения.

## Что сделать (ФТ-13.5)

1. **Редактирование конфигурации**: источники и роли, политики приёма, манифест и словари, шаблоны и правила сортировки, правила реакции и шаблоны текстов, матрица прав, приоритеты, TTL, сроки хранения, нормативы и пороги. Админка редактирует **те же структуры, что и YAML-файлы**: изменение проходит ту же pydantic-проверку, получает версию и коммитится в git (или пишется в файл, который затем коммитится — выбери и зафиксируй).
2. **Dry-run из интерфейса**: прогон правила по истории перед включением.
3. **Просмотр трасс**: то же, что `/trace`, `/stuck`, `/queue`, с фильтрами по источнику, модулю, аккаунту и коду причины; метрики этапов (медиана, p95).
4. **Пул**: состояния аккаунтов, паузы, бюджет, обязанности, покрытие чатов; добавление и вывод аккаунта (вход в аккаунт по-прежнему через CLI-утилиту).
5. **Доступ**: вход только для ролей admin и dev (расширяется матрицей прав), все изменения — с автором в журнале. Админка не открывает прямой доступ к БД извне (НФТ-20).

## Критерии приёмки этапа 5
1. Изменение через админку равнозначно правке файла: тот же результат, та же проверка, та же версия в журнале.
2. Невалидное изменение отклоняется с понятной ошибкой, действующая конфигурация не меняется.
3. Трассы и пул в интерфейсе совпадают с выводом команд `/trace` и `/accounts`.
