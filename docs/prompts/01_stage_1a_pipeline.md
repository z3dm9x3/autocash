# Этап 1a. Сквозной конвейер событий

> Контекст проекта — в `CLAUDE.md` (00_context). Этап 1 «Ядро» разбит на три промта: 1a (конвейер), 1b (пул и отправка), 1c (наблюдаемость и приёмка). Это 1a.

## Цель

Сообщение, написанное в чат, проходит всю цепочку `Gateway → … → Вывод`, получает тип и попадает в модуль за ≤ 1 с. Задача имеет трассу. Работаем с одним аккаунтом, но всё, что касается аккаунтов, уже спроектировано под пул (1b подключит планировщик, не переписывая конвейер).

## Что сделать

### 1. Каркас и конфигурация (ФТ-13.1–13.4)
- Структура пакета: `core/` (gateway, extractor, buffer, uploader, storage, sorter, queue, output, trace, config), `modules/`, `actions/`, `cli/`.
- YAML-конфиг с pydantic-схемой: источники и роли, политики приёма, манифест и словари, шаблоны и правила сортировки, приоритеты, сроки хранения, интервалы пачек, нормативы.
- Невалидный конфиг не применяется: действует прежняя версия, ошибка уходит в группу `logs`. Перезагрузка без рестарта (команда появится в 1c, механизм нужен сейчас).
- Каждая запись журнала и трасса хранит версию конфига, действовавшую в момент события.

### 2. Gateway (ФТ-2.1–2.4, 2.9–2.11)
- Обёртка над клиентом Telegram за интерфейсом (см. правило 2 в контексте). Приём новых сообщений, правок и удалений через push-обновления.
- Каждое событие получает `trace_id` и отметку аккаунта.
- Политики источника: `full` (сохранить и обработать), `meta` (факт и время), `presence` (факт существования чата), `ignore`. По умолчанию: `channel` → presence, группы логов Системы → ignore, новый чат без роли → политика из конфига и уведомление в `logs`.
- Роль отправителя определяется по `user_id`. Пересланное сообщение принадлежит переславшему. Анонимный админ — сообщение чата без прав на команды.
- Свои сообщения распознаются по `user_id` аккаунтов пула, в том числе когда приходят входящими на другой аккаунт: `origin=system` (ушло через Вывод) или `origin=human` (написано вручную). Правила реакции срабатывают только на внешних отправителей.
- Дедупликация: в супергруппах (`-100…`) точная по `chat_id + msg_id`; в обычных группах приблизительная по отправителю, времени и хешу текста, с пометкой источника.

### 3. Extractor (ФТ-3.1–3.9)
- Метаданные: аккаунт, chat_id, msg_id, отправитель, время сообщения, правки и приёма, reply_to, origin, тип медиа и ссылка на файл, номер версии, хеш текста, версия манифеста, trace_id.
- Нормализованный текст хранится целиком. Разметка Telegram очищается: `[1481598133](tel:1481598133)` → `1481598133`.
- Признаки по манифесту: числа по длине; суммы (`5 001.34`, `3500.00`, `4 001,36`); телефоны, карты, @username, ссылки; заголовок в `[…]`; пары `Метка: значение`; слова из словарей после нормализации (регистр, ё→е, транслит, начальная форма); маркеры (✅ ❌ 🔴 …); команды.
- Подполя по шаблону: `Пользователь: @x ID: 7287295969` → имя + TGID; `Успешных депозитов: 🔴 52 (всего: 52)` → маркер + два числа; `Метод оплаты: … 3 000 - 500 000` → метод + лимиты.
- Каждый признак сохраняется с позицией и ближайшей меткой. **Смысл признака здесь не назначается**, это делает сортировщик.
- Regex манифеста проверяются при загрузке и выполняются по А-7. Применяется только манифест, прошедший проверку. При смене версии манифеста признаки пересчитываются для сообщений, чей текст ещё хранится.
- Команды помечаются (А-5).

### 4. Буфер SQLite (ФТ-4.1, 4.3, 4.5, 4.6, А-6)
- Коммит в SQLite = событие принято. WAL + `synchronous=FULL`, пачки, отдельный поток.
- При старте проверь фактические `journal_mode` и `synchronous`: при расхождении — тревога и остановка.
- Запись помечается выгруженной после подтверждения коммита в PG и хранится резервный срок (конфиг).
- Лимит по диску: на подходе — тревога; при достижении принимаем только источники высшего приоритета.

### 5. Uploader (ФТ-4.2, 4.4, А-1, А-2, А-5, п. 3.3)
- Пачки по таймеру или по счёту, одна транзакция, порядок поступления, upsert по `(аккаунт, chat_id, msg_id, версия)`.
- После коммита пачка передаётся сортировщику в памяти. Пачка с командой уходит сразу.
- PG недоступен: приём и SQLite продолжают работать, сортировка и модули ждут, задачи получают «ожидает» с `DB_UNAVAILABLE`. После восстановления выгрузка накопленного по порядку, обработка догоняет поток.

### 6. Схема PostgreSQL (ФТ-5.1–5.6)
- `messages` с разбиением по месяцам: метаданные, текст, признаки, после сортировки — тип и поля (JSONB). Новая версия создаётся при изменении текста. Срок хранения текста задаётся по типу: по истечении удалить или архивировать (zstd со словарём), извлечённые поля хранятся бессрочно. Старое удаляется отключением разделов.
- Таблицы ядра: пул аккаунтов и журнал состояний, паузы FloodWait, карта членства, распределение обязанностей, источники и роли, пользователи Telegram с историей имён и ролями сотрудников, общее хранилище сущностей `(тип, ключ, состояние, атрибуты JSONB)` и связи, состояния диалогов, исходящие задачи и попытки, трассы, журнал срабатываний правил, отметки обработки модулей.
- Таблицы пула и членства создай сейчас, логику наполнит этап 1b.
- Общий пакетный писатель для модулей (А-4).

### 7. Сортировщик (ФТ-6.1–6.5)
- Правила из конфига. Условия над ролью источника, ролью отправителя, заголовком, словами, метками и признаками.
- Правило задаёт: сопоставление меток полям (`Номер счёта` → `mel_id`), ключ упорядочения, класс приоритета, срок хранения текста.
- Правила группируются в шаблоны. Источник ссылается на шаблон и переопределяет его часть.
- Нет подходящего правила → тип `unknown`, финал «пропущено» с `UNKNOWN_TYPE`, счётчик по источнику, периодическая сводка в `debug`.
- После рестарта сортировщик читает PG со своей отметки.

### 8. Менеджер очереди (ФТ-7.1–7.7)
- Подписки модулей на типы, в том числе по маске (`deposit.*`, `*`). Доставка всем подписчикам.
- У каждого модуля ограниченная очередь и свой лимит параллельности. Три полосы: команды → живой поток → backfill (backfill идёт, пока живая полоса ниже порога, с ограничением скорости). Внутри полосы — приоритет из конфига.
- Один ключ упорядочения обрабатывается строго последовательно, разные — параллельно. **Порядок по ключу старше полос**: если по ключу есть необработанный backfill, живые события ключа ждут, а backfill ключа поднимается в приоритете.
- Превышение порога длины очереди или задержки → предупреждение в `logs`. Отметка последнего обработанного события на модуль, продолжение с неё после рестарта.

### 9. API модулей (ФТ-8.1–8.3, 8.11)
- Модуль объявляет: подписки, сущности и место хранения, команды, раздел конфига, лимит параллельности, таймаут события.
- Обработка идемпотентна. Внешние действия создают исходящие задачи **в одной транзакции** с отметкой модуля; уникальный ключ «событие + правило».
- Ошибка или таймаут → `MODULE_ERROR` / `MODULE_TIMEOUT`, очередь модуля продолжает работу.
- Сделай один демонстрационный модуль (например, счётчик сообщений по источнику с ответом на `/ping`), чтобы прогнать конвейер насквозь.

### 10. Вывод — минимальный (ФТ-9.1, 9.3)
- Исходящие задачи с трассой. Отправка с одного аккаунта последовательно. `random_id` сохраняется до отправки, повтор идёт с тем же `random_id`, `RANDOM_ID_DUPLICATE` → «доставлено».
- Все вызовы API уже идут через интерфейс лимитера (простой вариант; полную логику даст 1b).

### 11. Трасса — базовая (ФТ-11.1, 11.2, 11.6)
- Этапы входящей задачи: принято → извлечено → в буфере → в PostgreSQL → отсортировано → в очереди модуля → обработано модулем (последние два — отдельно для каждого подписчика). Синхронная и пакетная запись согласно инварианту 5.

## Вне рамок 1a
Планировщик, несколько аккаунтов, подстраховочный опрос, догон, полный лимитер, команды отладки, модули «Заявки» и «Игроки», движок правил реакции, backfill.

## Критерии приёмки 1a (каждый — тест)
1. Сообщение из источника `full` попадает в PG, получает тип и доходит до демо-модуля за ≤ 1 с (p95 на прогоне 1000 сообщений с фейковым Telegram).
2. Правка создаёт новую версию, удаление фиксируется. Повторная выгрузка той же пачки ничего не меняет.
3. PG остановлен: приём продолжается, задачи в `DB_UNAVAILABLE`; после старта PG всё выгружено по порядку и обработано один раз.
4. `kill -9` процесса между коммитом SQLite и коммитом PG: после старта всё подтверждённое обработано ровно один раз.
5. Неправильная SQLite-прагма → остановка с тревогой. Невалидный конфиг или манифест → действует прежняя версия, ошибка в `logs`.
6. Порядок по ключу соблюдается при параллельной обработке разных ключей. Медленный модуль не задерживает другой модуль.
7. `unknown` получает `UNKNOWN_TYPE` и учитывается в счётчике источника.
8. Очистка разметки и извлечение всех форм признаков из примеров ТЗ покрыты unit-тестами.
