# Этап 2. Модули «Заявки» и «Игроки» + шаблон типовой кассы

> Контекст — `CLAUDE.md`. Ядро (этап 1) принято. На этих двух модулях проверяется конструктор: если для них приходится менять ядро ради предметной логики, значит нарушен П-1. Такое изменение вынеси в общее действие ядра и запиши в `docs/decisions.md`.

## Перед началом — обязательно

1. **Нужны образцы.** Мне понадобится записанная история касс в `tests/fixtures/messages/`: сообщения бота кассы всех видов («[ДЕПОЗИТ ТРЕУГОЛЬНИК]», «[ДЕПОЗИТ ПРЕДУСТАНОВЛЕННАЯ СУММА]», «[ДЕПОЗИТ]», «Реквизиты успешно отправлены пользователю ID …», ответы на `/turn_off`, `/turn_on`, `/change_dep_limits`), сообщения кассиров с реквизитами, правки с ✅/❌ и отменами. Если фикстур нет или не хватает видов — **остановись и попроси**, не выдумывай форматы.
2. **ФТ-З.9 — открытый вопрос**: отвечают ли кассиры reply на заявку. Реализуй оба способа привязки реквизитов (по `reply_to` и по следующему подтверждению бота с TGID), выбор и порядок — через конфиг. Учти, что кассир может отправить два набора реквизитов подряд.

## Что сделать

### 1. Внутренние действия ядра (ФТ-8.4, часть)
Реализуй как общие действия ядра, не внутри модулей:
- `match` — поиск совпадений: точный, нечёткий, в окне времени; возвращает кандидатов с оценкой. Нечёткий поиск выполняется в отдельном процессе (А-7).
- `lookup` / `upsert` — поиск, создание и обновление сущности в общем хранилище или таблице модуля.
- `link` — связь сообщения с сущностью или сущностей между собой.
- `set_state` — смена состояния сущности, в том числе с таймаутом.
- `report` — список или сводка по именованному запросу.

### 2. Шаблон типовой кассы (ФТ-6.3)
- Один шаблон правил сортировки для всех ~100 типовых касс. Источник ссылается на шаблон и переопределяет его часть.
- Сопоставление меток полям: `Номер счёта` → `mel_id`, `ID` → `tgid`, Deposit ID, сумма, бонус, метод, лимиты, маркеры.
- Ключ упорядочения — Deposit ID (если его нет — чат).

### 3. Модуль «Заявки» (ФТ-З.1–З.11)
- Касса — источник с ролью `kassa` по `chat_id`. Кассиры — один или несколько пользователей с ролью `casher` в этой кассе.
- Метод оплаты идентифицируется по названию без лимитов и по `method_id` из `/change_dep_limits N`, `/turn_on N`, `/turn_off N` и ответов бота. История лимитов и включений хранится.
- Ключ заявки — Deposit ID, общий для всех касс.
- Стадии и время каждой:

| Стадия | Сообщение-источник | Связь с заявкой |
|---|---|---|
| создана | «[ДЕПОЗИТ ТРЕУГОЛЬНИК]», «[ДЕПОЗИТ ПРЕДУСТАНОВЛЕННАЯ СУММА]» и др. | Deposit ID |
| реквизиты выданы кассиром | сообщение кассира с реквизитами | reply_to или следующее подтверждение бота с TGID |
| реквизиты отправлены игроку | «Реквизиты успешно отправлены пользователю ID …» (бонус, итоговая сумма) | TGID + чат + открытая заявка |
| чек получен | «[ДЕПОЗИТ]» | Deposit ID; сумма = запрошенная + бонус |
| финал ✅ / ❌ | правка сообщения «[ДЕПОЗИТ]» | Deposit ID |
| отменена | правка сообщения «создана» (инициатор, причина) | Deposit ID |
| перенаправлена | ответ бота на `/turn_off` | метод + открытые заявки |

- До финала отслеживаются все правки сообщений заявки; заявка живёт от секунд до нескольких дней. После финала (✅, ❌, отмена) статус фиксируется и заявка закрывается.
- При перенаправлении заявка сохраняет историю касс.
- Заявка без Deposit ID (например, у TRUSTED-пользователей) связывается по TGID, сумме и времени через `match`. OCR-предупреждения прикрепляются к заявке как отметки.
- Статистика по кассе, кассиру и периоду: число заявок и средняя сумма, время выдачи реквизитов и время до финала, доли успешных/отклонённых/отменённых, время работы и простоя методов. Граница суток — по часовому поясу из конфига.
- Сверка: заявки без финала старше X минут периодически перечитываются из Telegram пачкой id по чату, в рамках бюджета (приоритет 3). Реализуй здесь хук сверки из этапа 1b.
- Без финала дольше Y часов → статус «зависла», попадание в сводку сотрудникам, отдельный учёт в статистике. X и Y — OPEN-QUESTION, задаются в конфиге.
- Подключи резолвер Deposit ID к `/trace`.
- Номера карт и телефонов в реквизитах хранятся маскированными или зашифрованными (инвариант 8).

### 4. Модуль «Игроки» (ФТ-И.1–И.5)
- Идентификаторы: TGID и MelID. Каждая заявка добавляет связь TGID ↔ MelID. Игрок — связная компонента графа идентификаторов (union-find или эквивалент).
- Слияние по TGID и MelID; имя и username хранятся как история.
- Каждое слияние пишется в журнал; есть ручное разделение. Слияние групп крупнее порога (конфиг) требует подтверждения сотрудника, до подтверждения группы остаются раздельными.
- Запросы: депозиты игрока по всем кассам за период; список TGID и MelID игрока.
- Хранилище санкций и отметок: страйки (scam), блокировка/разблокировка (unban), жалобы, обращения, заметки операторов, у каждой записи автор и время. Команды `scam`/`unban` подключатся на этапе 3; здесь нужны модель данных и действия.

### 5. Команды отчётов (ФТ-12.5, 12.6)
- `/summ` и другие отчёты по кассе, кассиру, методу и периоду — из агрегатов, ответ ≤ 1 с; тяжёлые — с подтверждением и доставкой по готовности.
- Аргумент-идентификатор: TGID или MelID. Префикс `mel:` / `tg:` задаёт тип явно; без префикса поиск идёт по обоим, а при двух разных игроках бот просит уточнить.
- Права — по матрице из этапа 1c.

## Вне рамок
Автоответы, личные сообщения игрокам, `ask`, `scam`/`unban` как команды-правила (этап 3); backfill (этап 4).

## Критерии приёмки этапа 2
1. На записанной истории касс стадии заявок определены верно. Сделай эталонную разметку на фикстурах и тест, сравнивающий результат с эталоном.
2. Доля `unknown` среди сообщений бота кассы ниже порога из конфига (OPEN-QUESTION). Отчёт о доле — в тестах и в сводке `debug`.
3. Два набора реквизитов подряд, перенаправление, отмена, правка ✅→❌ до финала и заявка без Deposit ID обрабатываются правильно (отдельные тесты).
4. Повторная обработка той же истории даёт идентичное состояние заявок и игроков.
5. Слияние игроков по общему MelID работает, крупное слияние ждёт подтверждения, ручное разделение откатывает связи.
6. Отчёты отвечают ≤ 1 с на объёме ×10 от текущего (синтетика).
