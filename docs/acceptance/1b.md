# Этап 1b — критерии приёмки и тесты

Запуск: `python -m pytest -q`. Все тесты идут на фейковом Telegram (`tests/fake_telegram/server.py`) и настоящем PostgreSQL.

| № | Критерий | Тест |
|---|---|---|

| 2 | Догон 100 чатов без единого FloodWait (фейк выдаёт FloodWait выше 5 вызовов в секунду) | `test_pool_dynamics.py::test_catch_up_of_100_chats_without_a_single_flood_wait` |
| 3 | FloodWait → `paused`, пауза в БД переживает рестарт, обязанности переходят к другим, по окончании аккаунт возвращается | `tests/acceptance/test_pool_failures.py::test_flood_wait_pauses_account_survives_restart_and_duties_move` |
| 4 | PEER_FLOOD → `restricted` + тревога через другой аккаунт; приём на нём продолжается | `test_pool_failures.py::test_peer_flood_restricts_account_alarm_goes_through_another_one` |
| 5 | Бан → `lost`, тревога; групповые задачи ушли другим, личные ждут с `ACCOUNT_LOST` и по TTL получают `TTL_EXPIRED` | `test_pool_failures.py::test_ban_loses_account_group_tasks_move_private_ones_wait_and_expire` |

## Чего тесты не проверяют

- **Живой Telegram.** Новые части адаптера (`get_dialogs`, `get_channel_difference`, события вступления и исключения, вход через `autocash.cli.login`) на настоящих аккаунтах не запускались. Реальные пороги FloodWait и PEER_FLOOD неизвестны; дефолты темпа — оценка (D-1b-4).
- **Темп отправки (ФТ-9.7).** Код есть, но приёмочные тесты идут с отключённым темпом; отдельного теста на интервалы отправки нет.
- **Обрыв соединения без потери аккаунта** (`disconnected` → переподключение → догон): отдельного теста нет, покрыты рестарт и бан.
- **Команда администратора** для добавления и вывода аккаунта — этап 1c (D-1b-3).
- **Догон личных диалогов и обычных групп** после простоя (D-1b-10).
- **Часы Windows.** Лимитер считает интервалы по часам event loop, которые на Windows идут шагом ~16 мс; на Linux шаг наносекундный. Точность темпа на целевой ОС не измерялась.
