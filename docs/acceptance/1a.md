# Этап 1a — критерии приёмки и тесты

Запуск: `python -m pytest -q` (нужны бинарники PostgreSQL 16+: `AUTOCASH_PG_BIN` или `PATH`).

| № | Критерий | Тест |
|---|---|---|
| 1 | Сообщение из источника `full` попадает в PG, получает тип и доходит до демо-модуля за ≤ 1 с (p95 на 1000 сообщений) | `tests/acceptance/test_pipeline.py::test_message_goes_through_the_whole_chain`, `::test_latency_p95_under_one_second_on_1000_messages` (темп 50/с — решение D-1a-5) |
| 2 | Правка создаёт новую версию, удаление фиксируется; повторная выгрузка пачки ничего не меняет | `test_pipeline.py::test_edit_creates_version_and_delete_is_recorded`, `::test_repeated_upload_of_the_same_batch_changes_nothing` |
| 3 | PG остановлен: приём продолжается, задачи в `DB_UNAVAILABLE`; после старта всё выгружено по порядку и обработано один раз | `tests/acceptance/test_resilience.py::test_postgres_outage_intake_continues_then_everything_is_processed_once` |
| 4 | `kill -9` между коммитом SQLite и коммитом PG: всё подтверждённое обработано ровно один раз | `tests/acceptance/test_crash.py::test_kill_9_everything_accepted_is_processed_exactly_once` — 5 точек падения: до и после коммита PG, до и после коммита результата модуля |
| 5 | Неправильная SQLite-прагма → остановка с тревогой; невалидный конфиг или манифест → действует прежняя версия, ошибка в `logs` | `test_resilience.py::test_wrong_sqlite_pragma_stops_with_an_alarm`, `::test_invalid_config_keeps_previous_version_and_reports_to_logs` (схема, манифест, правило, YAML), `::test_valid_reload_applies_without_restart_and_is_versioned` |
| 6 | Порядок по ключу при параллельной обработке разных ключей; медленный модуль не задерживает другой | `tests/acceptance/test_queue_order.py::test_same_key_is_sequential_and_different_keys_are_parallel`, `::test_slow_module_does_not_delay_another_module`, `tests/unit/test_queue.py` (полосы, приоритет, порядок по ключу старше полос) |
| 7 | `unknown` получает `UNKNOWN_TYPE` и учитывается в счётчике источника | `test_pipeline.py::test_unknown_gets_reason_and_is_counted` |
| 8 | Очистка разметки и извлечение всех форм признаков из примеров ТЗ | `tests/unit/test_extractor.py` |

Дополнительно покрыто:

| Требование | Тест |

| ФТ-8.11: `MODULE_ERROR` / `MODULE_TIMEOUT`, очередь модуля продолжает работу | `test_queue_order.py::test_module_error_and_timeout_get_reason_codes_and_queue_goes_on` |
| ФТ-9.1, 9.3, 2.10: ответ на команду через Вывод, `random_id` до отправки, своё сообщение — `origin=system` | `test_pipeline.py::test_ping_command_is_answered_once_and_own_reply_is_system` |

## Чего тесты не проверяют

- **Работа с настоящим Telegram.** Адаптер `autocash/core/telegram/telethon_client.py` и запуск `python -m autocash.cli.run` на живом аккаунте не проверялись: реальные аккаунты в автотестах запрещены. Покрыто только преобразование обновлений и ошибок.
- **Целевое железо и Linux.** Все прогоны — на Windows-машине разработки. Задержку и потолок пропускной способности нужно перемерить на сервере 2 × 2 ГГц.
- **Реальные форматы сообщений.** Фикстур НФТ-21 нет; использованы только примеры из текста ТЗ.
- **Повтор отправки после падения в момент «отправка».** Логика есть (тот же `random_id`), сквозной тест с падением — критерий этапа 1c.
- **Архивирование текста zstd** (ФТ-5.3): реализовано удаление текста по сроку; архив не сделан.
